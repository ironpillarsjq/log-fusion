## 1. 现状盘点（含 RawLogFileWriter 的真实行为）

**好消息：原始字节已经在存了**，`RawLogFileWriter` 就是这条链路的起点，不用从零做。
但它现在的形态**不足以支撑存证**，需要改造。逐条对上：

| 现状（`RawLogFileWriter.java`） | 存证需要什么 | 差距 |
|---|---|---|
| 按平台写两个文件：`data/windows/raw-logs.log`、`data/linux/raw-logs.log` | 按 客户端 / 日期 / 小时 分段 | 要改分段策略 |
| `append(platform, rawBody)` 写的是**整个请求体**（Fluent Bit 发来的 JSON 数组），末尾补一个 `\n` | 一行原始日志一条存证，每条的绝对字节区间 | 要改成按记录切分并返回 offset/length |
| `Files.write(..., CREATE, WRITE, APPEND)`，**不返回写入位置** | 必须拿到该条起始 offset | 要改用 `FileChannel`（APPEND 模式下拿不到 position） |
| `synchronized (writeLock)` 单锁串行 | 并发安全，同一文件不能两条拿到同一 offset | 思路正确，改造后要按文件粒度或路径 key 加锁 |
| 只写文件，不记录任何元数据 | 要写 `audit_log_evidence`（路径/offset/length/hash） | 新增表与写入 |
| 路径是相对启动目录的固定值 | 存储根目录要可配置、读取时要防止目录穿越 | 新增配置项 + 根目录约束 |
| 没有 `force` 落盘 | 存证要求先落盘再写元数据 | 追加后 `channel.force(false)` |

其它与本模块相关的现状：

| 项 | 实际情况 |
|---|---|
| 工程 | `com.inspection.logbackend`，Spring Boot **4.0.6**，Java 17，Lombok，Maven（`mvnw`） |
| 数据访问 | `spring-boot-starter-jdbc`（`JdbcTemplate`）；`NamedParameterJdbcTemplate` 也在类路径上可直接用 |
| JSON | **Jackson 3**：`tools.jackson.databind.ObjectMapper` |
| 校验 | pom 里**没有** `spring-boot-starter-validation` |
| 建表 | **没有 Flyway**，SQL 需手工执行并留档 |
| 数据库 | MySQL `192.168.5.6:3306`，JDBC URL **没有默认库**，SQL 必须写 `` `库名`.`表名` `` |
| 端口 | 未配置 `server.port`，默认 **8080**，与前端 Vite 代理一致 ✓ |
| 现有接收接口 | `POST /api/v1/logs/windows`、`POST /api/v1/logs/linux`（body 是原始 JSON 字符串，返回 200 空响应） |
| 现有入库链路 | `LogController` → `LogIngestionService.ingest()` → ①`RawLogFileWriter` 落原文 ②`PythonLogProcessor` 调 Python 归一化 ③`LogRepository.save()` 写分类表 |
| 七张分类表 | 库 `log-linux`，**当前没有 `id` 主键**（融合日志契约 §5.1 会补上加） |

## 2. 与指南的差异

| 指南写法 | 本项目实际 | 怎么办 |
|---|---|---|
| `spring-boot-starter-validation` 的 `@Valid / @Pattern / @Size` | **没这个依赖** | 参数校验自己写显式判断（5.6 给法），或先加依赖 |
| Flyway `V5__create_audit_log_evidence.sql` | **没有 Flyway** | SQL 放 `docs/sql/`，手工执行留档 |
| 表建在 `log-linux`（指南 datasource 指向该库） | 本项目的库分工是 `log-linux`（分类表）+ `windows_logs`（Windows 事件）+ 建议新增 `log_monitor`（融合索引/存证/心跳） | 本表建议建在 **`log_monitor`**，与融合日志模块的 `audit_log_index` 同库，便于关联查询 |
| `created_at DEFAULT CURRENT_TIMESTAMP(6)` | JDBC URL 是 `serverTimezone=Asia/Shanghai`，而 `event_time` 由 Java 按 **UTC** 写入 | `received_at` / `last_verified_at` **必须显式写 UTC**；`created_at`/`updated_at` 建议也显式写，避免同一张表出现两种时间基准 |
| `com.fasterxml.jackson.databind.ObjectMapper` | Jackson 3：`tools.jackson.databind.ObjectMapper` | 沿用 `LogRepository` 里已有的写法 |
| 原始字节来自 `request.getRawPayload()` | 现有链路是**先把整个请求体落文件、再交给 Python 解析**，没有按记录切分 | 见第 3.1 节，这是本模块最关键的决策 |
| 存储根目录 `D:/audit-evidence` | 现有配置前缀是 `log-storage:` / `log-processing:` / `log-database:` | 沿用风格新增 `log-evidence:`（5.1），不要引入第三种命名风格 |
| `RawEvidenceStorage` 全新接口 | 已有 `RawLogFileWriter`（正在生产使用） | 保留它不动或直接演进，见 5.3 |

## 3. 必须先定的两件事

### 3.1 哈希输入到底是什么（**最关键**）

指南 §3.1 要求：

```text
raw_hash = SHA-256(raw_record_bytes)
```

并明确禁止：解析后重排键值、压缩空格、互换换行、按系统默认编码转换、**把 JSON 重新序列化**。

问题是：**你们现在的输入是 Fluent Bit 发来的 JSON**，`LogController` 收到的是
`@RequestBody String body`，而 body 里可能是**一个 JSON 数组**（多条记录）。
这时"一条记录的原始字节"并不天然存在。三个选择：

#### 方案 A（推荐）：让 Fluent Bit 一行一条

Fluent Bit 每次请求只发**一条**日志（单个 JSON 对象），或改成 NDJSON（每行一个 JSON 对象）。
那么：

```text
raw_record_bytes = 请求体字节，去掉末尾用于分隔的换行
raw_hash         = SHA-256(raw_record_bytes)
```

- 语义清晰、可验证：把这段字节原样写入分段文件，之后按 offset/length 读出来重算即可；
- **Python 侧不用改**：`src/main/python/linux/process_logs.py` 与 `windows/process_logs.py`
  都已经兼容 `dict` 或 `list` 两种输入（`if isinstance(payload, dict): payload = [payload]`）；
- 代价：请求数变多（每 5 秒一次心跳的量级完全可接受；日志是批量发送的，
  Fluent Bit 的 http output 有 `json_date_key`/`Retry_Limit` 等参数，改成一行一条需要评估吞吐）。

#### 方案 B（不改 Fluent Bit）：流式解析取字节区间

用流式 JSON 解析器逐元素读取，记录每个元素的字节起止位置，再据此切片：

```java
// 伪代码：bodyBytes 是完整的请求体字节
JsonParser parser = objectMapper.createParser(bodyBytes);
// 依赖 JsonLocation#getByteOffset() 拿到元素边界，
// 注意前导空白、转义字符、多字节 UTF-8 对 offset 的影响
```

- 好处：采集端配置完全不动；
- 风险：**offset 的准确性必须写测试验证**（含中文、转义引号、数组内嵌对象）；
  不同输入源（byte[] vs Reader）下 offset 语义不同，必须用 byte[] 解析；
- 如果采用，`algorithm_version` 仍然固定 `EVIDENCE-V1`，但**定义要在代码注释里写死并冻结**，
  一旦上线就不能再改切片规则，否则老数据全部 `HASH_MISMATCH`。

#### 方案 C（不推荐）：整段请求体做一次哈希

那是"批次存证"，指南第一阶段明确不实现。如果做，表结构里的 `category` /
`normalized_row_id` 就必须允许一对多，等于把第一阶段的模型推翻。**不要**先按 C 上线再改 A。

> **建议**：先按方案 A 实现并把规则写进代码注释与文档；如果 Fluent Bit 侧短期无法改成一行一条，
> 再用方案 B，并为"中文 / 转义 / 多字节 / 数组嵌套"各写一条测试。

### 3.2 `evidence_id` 怎么生成

指南 §5.3：库内用自增 `id` 做分页与关联，`evidence_id` 是展示与外部查询标识；
`VARCHAR(40)`、唯一键；单实例也建议 ULID，避免以后多实例迁移冲突。
但原型与指南示例展示的是 `EV-20261007-000128` 这种形式。两者二选一，**一旦上线不要改格式**：

| 方案 | 形态 | 实现 | 取舍 |
|---|---|---|---|
| ULID（推荐） | `01J9Z6K2M3N4P5Q6R7S8T9V0W1` | 自写 ~30 行 Crockford Base32 工具类，无第三方依赖 | 一次 INSERT 完成、天然按时间有序、多实例安全；展示形态与原型不同（前端只显示字符串，不解析） |
| `EV-日期-序号` | `EV-20261007-000128` | 先 INSERT 拿到自增 `id`，再 `UPDATE ... SET evidence_id = CONCAT('EV-', DATE_FORMAT(received_at,'%Y%m%d'), '-', LPAD(id,6,'0')) WHERE id = ?` | 与原型一致；每条多一次 UPDATE，多实例也安全（id 全局唯一） |

前端只做 `^[A-Za-z0-9-]{10,40}$` 的宽松校验，两种都接受。
ULID 参考实现（Java 17，无依赖）：

```java
public final class Ulid {
    private static final char[] ALPHABET = "0123456789ABCDEFGHJKMNPQRSTVWXYZ".toCharArray();
    private static final SecureRandom RANDOM = new SecureRandom();

    public static String next() {
        byte[] value = new byte[16];
        long time = System.currentTimeMillis();
        for (int i = 5; i >= 0; i--) { value[i] = (byte) (time & 0xFF); time >>>= 8; }
        byte[] random = new byte[10];
        RANDOM.nextBytes(random);
        System.arraycopy(random, 0, value, 6, 10);
        return encode(value);
    }

    private static String encode(byte[] value) {
        StringBuilder sb = new StringBuilder(26);
        // 128 bit -> 26 个 5bit 分组，首字符只用 3 bit
        int bitBuffer = 0, bitCount = 0, index = 0;
        for (byte b : value) {
            bitBuffer = (bitBuffer << 8) | (b & 0xFF);
            bitCount += 8;
            while (bitCount >= 5) {
                sb.append(ALPHABET[(bitBuffer >>> (bitCount - 5)) & 0x1F]);
                bitCount -= 5;
            }
        }
        if (bitCount > 0) sb.append(ALPHABET[(bitBuffer << (5 - bitCount)) & 0x1F]);
        return sb.substring(0, 26);
    }
}
```

## 4. 通用约定

### 4.1 统一响应结构

```json
{ "code": 0, "message": "success", "data": {} }
```

- 新增的 `/api/v1/evidence/**` 接口使用该结构（**`/export` 例外**，直接返回 CSV 文件）；
- 既有写入接口（`/api/v1/logs/windows`、`/logs/linux`、`/heartbeat`）返回值保持原样；
- `code != 0` 或 HTTP 4xx/5xx 时 **`message` 会原样展示给运维**，写中文可读文案。

响应类复用心跳/融合契约里的同一个类（`com.inspection.logbackend.web.ApiResponse`），异常兜底
限定到本模块包：

```java
@RestControllerAdvice(basePackages = "com.inspection.logbackend.evidence.controller")
```

### 4.2 时间、命名与取值

| 项 | 约定 |
|---|---|
| 时间格式 | UTC ISO 8601，如 `2026-10-07T13:31:19.265Z`；前端转本地时区显示 |
| 请求时间参数 | 只有 `startTime`（**没有 `endTime`**，见 6.2），值为带时区的 ISO 8601 |
| 字段命名 | JSON 一律小驼峰 `camelCase`；数据库列名下划线 |
| 空值 | `null`，不要 `""` |
| 分页 | `page` 从 1 开始；`size` 默认 50、**最大 100** |
| 哈希 | 响应里是**小写 64 位十六进制**字符串；库内存 `BINARY(32)`，用 `LOWER(HEX(raw_hash))` / `UNHEX(?)` |
| 默认范围 | 不传 `startTime` 时按**最近 24 小时** |

### 4.3 枚举（前后端必须一致）

**校验状态 `verifyStatus`**

| 值 | 中文 | 产生条件 |
|---|---|---|
| `PENDING` | 待校验 | 已保存并生成初始哈希，尚未重新校验 |
| `VALID` | 校验正常 | 原始字节存在，重算 SHA-256 与存证值一致 |
| `HASH_MISMATCH` | 哈希不一致 | 原始字节存在，但重算值与存证值不同 |
| `RAW_MISSING` | 原始日志缺失 | 文件不存在、被移走，或读不到指定范围（含权限不足、文件截断） |

**七个类别 `category`**：与融合日志模块完全相同，**权威定义只应有一份**（见第 10 节）：
`authentication_session`、`account_security_change`、`process_command_execution`、
`file_object_access`、`network_ipc_communication`、`system_service_audit_lifecycle`、
`security_policy_config_change`。未识别 type 时返回 `null`。

### 5.3 分段文件存储（改造 `RawLogFileWriter` 的能力）

**目录布局**（按客户端 + 日期 + 小时分段，避免单目录海量小文件）：

```text
{storage-root}/
└─ 2026/10/07/fb-linux-001/15/
   ├─ audit-000001.log
   └─ audit-000002.log
```

**写入格式**：`[原始字节][\n][原始字节][\n]...`，数据库里的 `raw_length` **不含**分隔换行。

```java
public interface RawEvidenceStorage {
    /** 追加一条原始字节，返回可精确定位的存储位置 */
    RawLocation append(String clientId, Instant receivedAt, byte[] rawBytes);

    /** 按路径 + offset + length 精确读取；读不到抛异常，由调用方归入 RAW_MISSING */
    byte[] read(String relativePath, long offset, int length);
}

public record RawLocation(String relativePath, long offset, int length) {}
```

关键实现要点（**这几条直接决定存证是否可信**）：

```java
@Service
public class SegmentFileEvidenceStorage implements RawEvidenceStorage {

    private final EvidenceStorageProperties properties;
    /** 按文件路径加锁：同一分段的"取 offset + 写入"必须是一个原子操作 */
    private final ConcurrentHashMap<String, Object> locks = new ConcurrentHashMap<>();

    @Override
    public RawLocation append(String clientId, Instant receivedAt, byte[] rawBytes) {
        Path file = resolveSegment(clientId, receivedAt);   // 按 客户端/日期/小时 定位分段文件
        String relative = properties.storageRoot().relativize(file).toString().replace('\\', '/');

        synchronized (locks.computeIfAbsent(relative, key -> new Object())) {
            try {
                Files.createDirectories(file.getParent());
                try (FileChannel channel = FileChannel.open(file,
                        StandardOpenOption.CREATE, StandardOpenOption.WRITE, StandardOpenOption.APPEND)) {
                    long offset = channel.size();          // ← 不能用 Files.write(APPEND)，那样拿不到位置
                    channel.write(ByteBuffer.wrap(rawBytes), offset);
                    channel.write(ByteBuffer.wrap(new byte[]{'\n'}), offset + rawBytes.length);
                    channel.force(false);                  // 先落盘，再写数据库元数据
                    return new RawLocation(relative, offset, rawBytes.length);
                }
            } catch (IOException e) {
                throw new UncheckedIOException("写入存证分段文件失败：" + relative, e);
            }
        }
    }

    @Override
    public byte[] read(String relativePath, long offset, int length) {
        Path root = properties.storageRoot();
        Path target = root.resolve(relativePath).normalize();
        // 目录穿越防护：必须限定在根目录内
        if (!target.startsWith(root)) {
            throw new SecurityException("存证路径越界：" + relativePath);
        }
        try (FileChannel channel = FileChannel.open(target, StandardOpenOption.READ)) {
            ByteBuffer buffer = ByteBuffer.allocate(length);
            channel.position(offset);
            while (buffer.hasRemaining()) {
                if (channel.read(buffer) < 0) {
                    throw new EOFException("存证文件长度不足：" + relativePath);
                }
            }
            return buffer.array();
        } catch (NoSuchFileException | EOFException e) {
            throw new EvidenceRawMissingException(relativePath, e);
        } catch (IOException e) {
            throw new EvidenceRawMissingException(relativePath, e);
        }
    }
}
```

**不要用 `Files.readAllLines()`**：它做字符解码与换行处理，还会把整个文件读进内存。
必须 `channel.position(offset)` + 精确读 `raw_length` 字节。放不下时按 `segment-max-bytes` 滚动到
`audit-000002.log`（`audit-%06d.log`）。

### 5.4 接收链路接入（事务边界）

文件系统与 MySQL 不能参加同一个本地事务。按指南 §8.9：

```text
1. 原始字节追加到分段文件并 force 落盘
2. 开启数据库事务
3. 写七类中的对应融合表（拿到分类表行 id）
4. 写 audit_log_evidence（文件位置 + 融合行 id + 哈希）
5. 提交数据库事务
```

落到你们的代码上，改动点在 `LogIngestionService.ingest()`：

```java
public int ingest(Platform platform, String rawBody) {
    // 1) 原文留档（既有行为，不动）
    if (platform == Platform.WINDOWS) rawLogFileWriter.appendWindows(rawBody);
    else rawLogFileWriter.appendLinux(rawBody);

    // 2) 归一化（既有行为，不动）
    List<Map<String, Object>> records = pythonLogProcessor.process(platform, rawBody);

    // 3) 新增：按记录切分原始字节 → 写分段文件 → 算哈希 → 同事务写分类表与存证表
    return evidenceIngestService.ingest(platform, rawBody, records);

```

`AuditEvidenceIngestService` 骨架：

```java
@Service
@RequiredArgsConstructor
public class AuditEvidenceIngestService {

    @Transactional
    public int ingest(Platform platform, String rawBody, List<Map<String, Object>> records) {
        List<RawRecord> rawRecords = rawRecordSplitter.split(rawBody, records);  // 见 3.1 方案 A/B

        int saved = 0;
        for (RawRecord raw : rawRecords) {
            Instant receivedAt = Instant.now();
            String clientId = raw.clientId();

            // 先文件、后数据库；文件写完但事务失败会产生"孤立片段"，可由后台按 offset 清理，不能截断文件
            RawLocation location = storage.append(clientId, receivedAt, raw.bytes());
            byte[] rawHash = HashUtils.sha256(raw.bytes());

            NormalizedReference reference = normalizationService.insertNormalized(platform, raw.record());

            evidenceRepository.insert(new EvidenceInsert(
                    evidenceIdGenerator.next(),   // ULID 或 EV-日期-序号，见 3.2
                    receivedAt, clientId, raw.hostname(), raw.sourceIp(),
                    reference.category(), raw.auditType(),
                    location, rawHash,
                    reference.table(), reference.rowId()));
            saved++;
        }
        return saved;
    }
}
```

**注意**：现有 `LogRepository.save()` 是 `batchUpdate` 一次性写分类表，**拿不到每条的自增 id**。
存证需要 `normalized_row_id`，所以要么改成逐条 `GeneratedKeyHolder`（10 台客户端的量足够），
要么保留批量而对存证关联先置 `NULL`。**如果 JDBC URL 以后加了
`rewriteBatchedStatements=true`，批量插入将拿不到每条的 id**，那时存证关联会写错——不要开这个参数。

```java
@Transactional
public VerifyResult verify(String evidenceId) {
    EvidenceRecord record = repository.requireByEvidenceId(evidenceId);
    VerifyStatus status;
    try {
        byte[] raw = storage.read(record.rawStoragePath(), record.rawOffset(), record.rawLength());
        byte[] actual = HashUtils.sha256(raw);
        // 必须用常量时间比较
        status = MessageDigest.isEqual(record.rawHash(), actual)
                ? VerifyStatus.VALID : VerifyStatus.HASH_MISMATCH;
    } catch (EvidenceRawMissingException e) {
        status = VerifyStatus.RAW_MISSING;
        log.warn("存证原始字节不可读 evidenceId={} path={} offset={} length={}",
                evidenceId, record.rawStoragePath(), record.rawOffset(), record.rawLength(), e);
    }
    Instant verifiedAt = Instant.now();
    repository.updateVerification(evidenceId, status, verifiedAt);   // 只更新这三列
    return new VerifyResult(evidenceId, status, verifiedAt);
}
```

**只更新 `verify_status` / `last_verified_at` / `updated_at`，绝不覆盖 `raw_hash`。**
也不要提供"重新生成并覆盖原始哈希"的普通接口——那等于失去证明日志被修改的能力。

### 5.6 查询 / 详情 / 导出

- 主机搜索只匹配 `hostname` 与 `source_ip` 两个固定列，`%`/`_`/反斜杠要转义：

## 7. 前端已有的容错

| 情况 | 前端行为 |
|---|---|
| 列表查询失败 / 超时（8 秒 → 存证接口 15 秒） | 顶部错误条 + 重试按钮，**保留上一次成功数据**，显示"数据更新时间" |
| 连续失败 ≥ 2 次 | 提示升级为"已连续 N 次查询失败" |
| 单条校验失败 | 只恢复该行按钮，**不清空列表** |
| 当前页校验部分失败 | 提示"已校验 N 条，发现 M 条异常" |
| 详情读取失败（404 或 rawLog 为 null） | 仍展示存证元数据，正文区显示"原始日志文件不存在或无法按 offset/length 读取" |
| `rawHash` 输入不是 64 位十六进制 | 前端先拦下并提示，不发请求；后端仍必须再校验 |
| 连续点击校验 | 同一条 ID 在途时忽略重复请求 |
| `total = 0` 时点导出 | 提示"当前没有可导出的存证记录"，不发请求 |
| 列表自动刷新 | **不自动刷新**，避免看详情/翻页时内容跳动（指南第 12 节） |
| `category` 为 null 的记录 | 表格"融合类别"列显示"未识别"，不报错 |

## 9. 验收清单

- [ ] 每条已接收日志都有独立 `evidence_id` 与 SHA-256，且**哈希针对保存的原始字节**计算
- [ ] 原始文件可按 `path + offset + length` 精确读出，且与写入字节逐字节一致
- [ ] `raw_length` 不含用于分隔记录的换行
- [ ] 追加与"取 offset"是一个原子操作（并发压测下无两条拿到同一 offset）
- [ ] 写入后 `force` 落盘，再写数据库元数据；事务失败不回滚文件、不截断文件
- [ ] 七类融合行可通过 `(normalized_table, normalized_row_id)` 反查到存证
- [ ] 列表可按主机/IP、类别、状态、时间、完整哈希组合查询；非法值 400
- [ ] `size > 100`、跨度 > 31 天、非 64 位哈希 返回 400
- [ ] 单条与当前页（≤100）校验能正确区分 `VALID` / `HASH_MISMATCH` / `RAW_MISSING`
- [ ] 重新校验**不会**覆盖 `raw_hash`
- [ ] 相对路径逃逸存储根目录时拒绝读取（`..\..` 用例）

## 10. 与融合日志模块的关系

两个模块共用一套类别定义与一个库，**请按下面的方式复用，不要各写一份**：

```
                      ┌──────────────────────────────┐
   Fluent Bit ───────▶│ LogController 接收原始字节     │
                      └──────────────┬───────────────┘
                                     │ 同一事务内
                     ┌───────────────┴────────────────┐
                     ▼                                ▼
        `log-linux`.七张融合分类表            `log_monitor`.audit_log_evidence
        （融合日志模块，需先补 id 主键）        （本模块，记录 raw_hash 与文件位置）
                     │                                │
                     ▼                                │
        `log_monitor`.audit_log_index                 │
        （总览检索索引，融合日志模块）                 │
                     ▲                                │
                     └──── normalized_row_id ─────────┘
```

三条硬约束：

1. **`audit_log_evidence.normalized_row_id` 指向分类表的 `id`**，而七张分类表现在**还没有 `id`**。
   所以**必须先执行融合日志契约 §5.1 的 `ALTER TABLE ... ADD COLUMN id ... ADD PRIMARY KEY (id)`**，
   本模块才能写出可用的融合关联。过渡期可以先写 `normalized_table`/`normalized_row_id = NULL`，
   等融合表补好 id 后再回填。
2. **类别枚举只应有一份权威定义**。融合日志契约里有 `LogCategoryDefinition`（含表名与字段白名单），
   本模块的 `EvidenceCategory` 只用到"键 + 中文名"。建议把两者合并为一个
   `com.inspection.logbackend.logs.config.AuditLogCategory` 枚举，存证模块引用它，
   避免以后新增类别时两处漂移。
3. **时间基准要一致**：分类表的 `ingested_at`（融合模块）与存证表的 `received_at`（本模块）
   是同一次接收的两个时间点，通常相差几毫秒。融合统计用 `ingested_at`，
   存证与"接收延迟"分析用 `received_at`，两者都由 Java 显式写 UTC，
   **都不要依赖 `DEFAULT CURRENT_TIMESTAMP`**。

## 11. 顺带发现的几个问题

1. **`RawLogFileWriter` 用的是 `APPEND` 模式，拿不到写入偏移**。存证必须知道每条记录的绝对
   offset，所以要么改成 `FileChannel` + `size()`（见 5.3），要么改设计。
   这是本模块改造量最大的一处，建议单独一个提交。
2. **`data/windows/raw-logs.log` 与 `data/linux/raw-logs.log` 是相对路径**，
   以应用**启动目录**为基准。用 `java -jar jar/log-backend.jar` 从 `jar/` 目录启动时，
   文件会落在 `jar/data/...`。存证存储根目录务必改成绝对路径并显式配置，否则换启动方式后
   数据库里的相对路径全部指向不存在的位置（表现为整页 `RAW_MISSING`）。
3. **数据库密码明文在三处**（`application.yml`、`windows/config.py`、
   `import_audit_csv_to_mysql.py`），且导入脚本里的 `MYSQL_HOST` 与 `application.yml` 不是同一台。
   存证涉及原始日志原文，建议优先处理：改环境变量 + 轮换密码 + 不要用 root 连应用。
4. **`LogController` 收到非法 JSON 时**没有 `@ExceptionHandler`，
   客户端拿到 Spring 默认 500，而 `openspec/specs/log-ingestion/spec.md` 期望 400。
   新增存证逻辑后，这条链路上的异常处理建议一并补齐——**存证的第一步是原始字节，
   如果请求体本身非法，应该明确拒收并计数，而不是写一半文件**。
