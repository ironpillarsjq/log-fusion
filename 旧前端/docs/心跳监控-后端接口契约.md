## 1. 现状盘点

| 项 | 实际情况 |
|---|---|
| 工程 | `D:\log-backend`，Maven（`mvnw`），`com.inspection.logbackend` |
| 框架 | Spring Boot **4.0.6**，Java 17，Lombok |
| 数据访问 | `spring-boot-starter-jdbc`（`JdbcTemplate`）+ mybatis-spring-boot-starter 4.0.1（`application.yml` 里 mybatis 配置仍是注释，标注 Phase 2） |
| JSON | **Jackson 3**：`tools.jackson.databind.ObjectMapper`（见 `LogRepository`） |
| 数据库 | MySQL `192.168.5.6:3306`，**两个库**：`windows_logs`（5 张表）、`log-linux`（7 张表）；JDBC URL **没有默认库**，所有 SQL 必须写全限定名 |
| 端口 | `application.yml` 未配 `server.port`，默认 **8080**，与前端 Vite 代理默认目标一致 ✓ |
| 已有写入接口 | `POST /api/v1/logs/windows`、`POST /api/v1/logs/linux`（`LogController`，Fluent Bit 调用，body 是原始 JSON 字符串，返回 200 空响应） |
| 已有心跳接口 | `POST /api/v1/heartbeat`（注意是**单数、无 s**），`HeartbeatController` |
| 已有定时任务 | `HeartbeatWatchdog`，`@Scheduled(fixedDelay = 3000)`，阈值 15 秒；`LogBackendApplication` 已带 `@EnableScheduling` |
| 尚未实现 | 前端要用的 5 个监控查询接口、心跳落库、按客户端的日志量统计、趋势快照 |

**心跳现状（关键）**：`HeartbeatController` 只用了一个内存表

```java
public static final ConcurrentHashMap<String, Long> clientLastSeenMap = new ConcurrentHashMap<>();
```

- key = `client_id`（Fluent Bit `modify` 插件注入，实际是客户端计算机名）
- value = 最后一次收到心跳的毫秒时间戳
- **不落库**：进程重启后全部丢失，也拿不到 IP、系统类型、Fluent Bit 版本
- `HeartbeatWatchdog` 超时 15 秒后执行 `iterator.remove()` 把条目**删掉**
  → 结果就是「离线的客户端在服务端彻底消失」，前端无法展示「离线」这一状态

## 2. 与指南的差异（照抄指南会踩的坑）

| 指南写法 | 本项目实际 | 怎么办 |
|---|---|---|
| Spring Boot 3 + JPA + Flyway | Spring Boot 4.0.6 + `JdbcTemplate`/MyBatis，无 JPA、无 Flyway | **不要**引 `spring-boot-starter-data-jpa`、`flyway-mysql`；本模块沿用 `JdbcTemplate`，与 `LogRepository` 风格一致 |
| `import com.fasterxml.jackson.databind.ObjectMapper` | Jackson 3：`tools.jackson.databind.ObjectMapper` | 直接沿用 `LogRepository` 里已有的写法，否则编译不过 |
| `POST /api/v1/heartbeats`，camelCase 请求体 | `POST /api/v1/heartbeat`，body 是 **JSON 数组**，字段 `client_id`（snake_case），返回纯文本 `"pong"` | **保持现有协议不动**（Fluent Bit 已在跑），只在其内部增加落库，见 4.1 |
| 心跳 5 秒、阈值 10/30 秒 | 看门狗阈值 15 秒，且超时删除内存条目 | 页面状态**不再依赖内存表**，改为查库计算 10/30 秒；看门狗保留用于告警，见 4.1 |
| 单库 `log-linux` | 两个库 `windows_logs` + `log-linux`（`log-linux` 带连字符，必须反引号） | 所有 SQL 用 `` `库名`.`表名` ``，新增监控表放 `log_monitor` 库，见第 6 节 |
| 七张日志表补 `source_client_id/ingested_at` | 是 **12 张表**（Windows 5 + Linux 7）；Windows 表有 `imported_at`，Linux 表两者都没有 | 统一给 12 张表加 `source_client_id` + `ingested_at`，见 6.2 |
| 统一响应 `{code,message,data}` | 现有接口没有统一响应结构（心跳返回 `"pong"`，日志返回空 200） | 只让**新增的 `/api/v1/monitor/**`** 用统一结构，既有接口不动 |
| `spring-boot-starter-validation` 做 DTO 校验 | pom 里没这个依赖 | 本契约的接口是 GET 查询，不需要；将来扩展心跳 DTO 再加 |

## 3. 通用约定

### 3.1 统一响应结构（仅用于新增的监控接口）

```json
{ "code": 0, "message": "success", "data": {} }
```

- `code = 0` 成功，前端只取 `data`；`code != 0` 或 HTTP 4xx/5xx 时
  **`message` 会原样显示给运维人员**，请写中文可读文案，
  例如 `"客户端不存在：fb-linux-007"`，不要写异常类名。
- 前端超时 8 秒，查询接口请在 8 秒内返回。
- 既有接口（`/api/v1/heartbeat`、`/api/v1/logs/**`）**返回值保持原样**，
  不要为了统一响应结构去改它们，Fluent Bit 依赖现有行为。

建议新增一个与既有风格一致的响应类（Java 17 record）：

```java
package com.inspection.logbackend.web;

public record ApiResponse<T>(int code, String message, T data) {
    public static <T> ApiResponse<T> ok(T data) { return new ApiResponse<>(0, "success", data); }
    public static <T> ApiResponse<T> fail(int code, String message) { return new ApiResponse<>(code, message, null); }
}
```

异常兜底（**注意限定包名**，否则会影响既有接口的错误响应）：

```java
package com.inspection.logbackend.web;

@RestControllerAdvice(basePackages = "com.inspection.logbackend.controller.monitor")
public class MonitorExceptionHandler {

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<ApiResponse<Void>> handleBadRequest(IllegalArgumentException e) {
        return ResponseEntity.badRequest().body(ApiResponse.fail(400, e.getMessage()));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiResponse<Void>> handleServerError(Exception e) {
        log.error("监控接口异常", e);
        return ResponseEntity.status(500).body(ApiResponse.fail(500, "服务端处理失败，请查看后端日志"));
    }
}
```

### 3.2 时间、命名与取值

| 项 | 约定 |
|---|---|
| 时间格式 | **UTC ISO 8601**，如 `2026-10-07T05:51:18.990Z`；前端负责转本地时区显示 |
| 字段命名 | JSON 一律小驼峰 `camelCase`（**只有心跳请求体是 snake_case，因为 Fluent Bit 已定死**） |
| 空值 | 用 `null`，不要 `""`，不要 `"-"` |
| 分页 | `page` **从 1 开始** |
| 布尔 | `true` / `false` |
| 百分比 | `onlineRate` 是 **0–100 的数值**（不是 0–1 小数） |
| 数据库时间 | `event_time` 现在就是按 UTC 存进 `DATETIME` 的（见 `LogRepository.setTimestamp`），新增的 `ingested_at` 沿用同一约定 |

### 3.3 枚举

**心跳状态 `heartbeatStatus`**（只允许后端判定，前端不重算）

| 值 | 中文 | 判定（`age = now - lastHeartbeatAt`） |
|---|---|---|
| `ONLINE` | 在线 | `age <= 10` 秒 |
| `DELAYED` | 延迟 | `10 < age <= 30` 秒 |
| `OFFLINE` | 离线 | `age > 30` 秒 |

**日志状态 `logStatus`**（与心跳状态**独立**）

| 值 | 中文 | v1 判定规则 |
|---|---|---|
| `NORMAL` | 正常 | `logs_last_5m > 0` |
| `NO_LOG` | 无日志 | 近 5 分钟 0 条，但心跳仍正常到达（低频业务服务器属正常现象） |
| `BACKLOG` | 积压 | 心跳里 `buffered_chunks > 0` —— **需要心跳新增该字段，当前恒不出现** |
| `INTERRUPTED` | 中断 | 心跳里 `output_healthy == false` —— **同上，当前恒不出现** |

> v1 只会出现 `NORMAL` / `NO_LOG`。等 Fluent Bit 的心跳里带上 `buffered_chunks`、
> `output_healthy`（见 4.1）后，`BACKLOG` / `INTERRUPTED` 自动生效，前端无需改动，
> 前端四种状态的样式已经写好。

**系统类型 `osType`**：`"Linux"` / `"Windows"`；实在推断不出来时返回 `"Unknown"`
（前端表格原样展示，系统筛选下拉里只有 Linux/Windows 两项）。

## 4. 需要改动的四处（按文件）

### 4.1 心跳落库 — `controller/HeartbeatController.java`

**保持现有对外协议不变**（路径 `/api/v1/heartbeat`、JSON 数组、`client_id`、返回 `"pong"`），
只在处理逻辑里加一次落库。这样 Fluent Bit 不用改配置，页面立刻有数据。

```java
@RestController
@RequestMapping("/api/v1")
@Slf4j
public class HeartbeatController {

    /** 保留：告警看门狗仍用它 */
    public static final ConcurrentHashMap<String, Long> clientLastSeenMap = new ConcurrentHashMap<>();

    private final CollectorClientRepository collectorClientRepository;

    public HeartbeatController(CollectorClientRepository collectorClientRepository) {
        this.collectorClientRepository = collectorClientRepository;
    }

    @PostMapping("/heartbeat")
    public ResponseEntity<String> handleHeartbeat(
            @RequestBody List<Map<String, Object>> payloadList,
            HttpServletRequest request) {

        Instant receivedAt = Instant.now();
        String remoteIp = request.getRemoteAddr();   // NAT/反代场景见下方说明

        for (Map<String, Object> payload : payloadList) {
            String clientId = text(payload.getOrDefault("client_id", "UNKNOWN_HOST"));
            clientLastSeenMap.put(clientId, receivedAt.toEpochMilli());
            collectorClientRepository.upsertHeartbeat(clientId, remoteIp, payload, receivedAt);
            log.info("收到来自客户端 [{}] 的健康心跳...", clientId);
        }
        return ResponseEntity.ok("pong");
    }
}
```

**`collector_client` 的 upsert（`CollectorClientRepository`，JdbcTemplate 写法）**

```java
private static final String UPSERT = """
        INSERT INTO `log_monitor`.`collector_client`
            (client_id, ip_address, server_name, os_type, os_version, fluent_bit_version,
             heartbeat_interval_sec, buffered_chunks, output_healthy,
             last_heartbeat_at, created_at, updated_at)
        VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
        ON DUPLICATE KEY UPDATE
            ip_address = VALUES(ip_address),
            server_name = VALUES(server_name),
            os_type = VALUES(os_type),
            os_version = VALUES(os_version),
            fluent_bit_version = VALUES(fluent_bit_version),
            heartbeat_interval_sec = VALUES(heartbeat_interval_sec),
            buffered_chunks = VALUES(buffered_chunks),
            output_healthy = VALUES(output_healthy),
            last_heartbeat_at = VALUES(last_heartbeat_at),
            updated_at = VALUES(updated_at)
        """;
```

**心跳里没有的字段怎么填**（当前 Fluent Bit 只保证 `client_id`，其余字段先给兜底值，
将来 Fluent Bit 补上就自动生效，后端代码不用改）：

| 字段 | 取值规则 |
|---|---|
| `client_id` | `payload["client_id"]`，必填 |
| `ip_address` | `request.getRemoteAddr()`（服务端看到的来源地址，比客户端自报更可信）；经 NAT/反代时只信任受控代理写入的 `X-Forwarded-For` |
| `server_name` | `payload` 里有就用；否则**用 `client_id` 兜底**（`client_id` 本身就是计算机名） |
| `os_type` | 优先级：`payload["os_type"]` → 按 `client_id` 推断（含 `win`/`windows` → `Windows`；含 `linux`/`fb-linux` → `Linux`）→ `"Unknown"` |
| `os_version` | `payload["os_version"]`，没有就落空串或 `Unknown` |
| `fluent_bit_version` | `payload["fluent_bit_version"]`，可空 |
| `heartbeat_interval_sec` | `payload` 里有就用，否则默认 `5` |
| `buffered_chunks` | `payload` 里有就用（int），否则 `0` |
| `output_healthy` | `payload` 里有就用（boolean），否则 `true` |
| `last_heartbeat_at` | **服务端接收时间** `Instant.now()`，**绝不能用客户端上报的时间** |
| `created_at` / `updated_at` | 同上 |

> **建议给 Fluent Bit 的 `heartbeat.conf` 加几个字段**（`modify` 插件或 http 插件参数），
> 数据就完整了：`server_name`、`os_type`、`os_version`、`fluent_bit_version`、
> `heartbeat_interval_sec`、`buffered_chunks`、`output_healthy`。
> 这一步不影响后端改动——按上表，后端代码两种情况下都能跑。

**关于 `HeartbeatWatchdog`**：15 秒阈值 + `iterator.remove()` 的逻辑**保留**，
它服务的是"掉线告警"（`executeFailureAction` 里的 TODO）。
但要注意：**页面状态不再从 `clientLastSeenMap` 读取**，因为条目被删掉后
离线客户端就查不到了。页面一律用 `collector_client.last_heartbeat_at` + 10/30 秒阈值在查询时算。
（顺带一提：注释写"每 5 秒巡检"，实际 `fixedDelay = 3000` 是 3 秒。）

### 4.2 新增查询接口 — `controller/monitor/MonitorController.java` + `service/MonitorService.java`

新增包 `controller.monitor`（不要混进现有 `controller` 包，方便 3.1 的异常处理只作用于新接口），
实现第 5 节的 4 个 GET 接口。计算规则：

1. 进入方法时取**一次** `Instant now = Instant.now()`，同一响应内所有客户端共用这个基准。
2. `SELECT` 出 `collector_client` 全部行（10 台，直接全查），在 Java 里算状态。
3. `heartbeatDelaySec = max(0, now - last_heartbeat_at)`；
   `heartbeatStatus` 按 3.3 的 10/30 秒阈值；
   `last_heartbeat_at` 为空的旧数据一律按 `OFFLINE` 处理。
4. 关键字、状态、系统类型筛选和分页都在 Java 里做（数据量小）；
   `heartbeatStatus` 是算出来的，**不能在 SQL 里筛**。
5. 稳定排序：`ORDER BY client_id ASC`（前端原型的顺序即 Linux 在前、Windows 在后）。
6. `total` 是**筛选后的总数**（给分页器用），不是全库总数。

关键查询：

```java
private static final String SELECT_ALL = """
        SELECT client_id, ip_address, server_name, os_type, os_version, fluent_bit_version,
               heartbeat_interval_sec, last_heartbeat_at, last_log_at, logs_last_5m,
               log_status, buffered_chunks, output_healthy, created_at, updated_at
        FROM `log_monitor`.`collector_client`
        ORDER BY client_id
        """;

private static final String SELECT_ONE = SELECT_ALL.replace("ORDER BY client_id", "WHERE client_id = ?");
```

`lastHeartbeatAt` 为空时，`RowMapper` 里读成 `null`，判定时当 `OFFLINE`：

```java
private HeartbeatStatus resolveStatus(Instant lastHeartbeatAt, Instant now) {
    if (lastHeartbeatAt == null) return HeartbeatStatus.OFFLINE;
    long age = Math.max(0, Duration.between(lastHeartbeatAt, now).toSeconds());
    if (age <= ONLINE_THRESHOLD_SEC) return HeartbeatStatus.ONLINE;      // 10
    if (age <= OFFLINE_THRESHOLD_SEC) return HeartbeatStatus.DELAYED;    // 30
    return HeartbeatStatus.OFFLINE;
}
```

阈值建议放进 `application.yml`（沿用你们现有 `log-*` 前缀风格）：

```yaml
monitor:
  online-threshold-seconds: 10
  offline-threshold-seconds: 30
```

### 4.3 按客户端的日志量 — `repository/LogRepository.java`

这一步是**唯一需要改动既有入库代码**的地方，也是「近 5 分钟日志量」「日志状态」的数据来源。

**第一步**：给 12 张表加两列（SQL 见 6.2），然后在 `LogRepository` 里把值写进去。
好消息是 `client_id` **已经在归一化结果里了**，两个平台都不用动 Python：

- **Windows**：`process_logs.py` 的 `normalize()` 已产出 `client_id`
  （现在被拼进了 `source_file`，见 `windowsSetter` 第 141 行）。
  在 `windowsInsertSql()` 的列尾追加 `` `source_client_id`, `ingested_at` ``，
  在 `windowsSetter` 末尾补两个 `setString(ps, 22, client)` / `setTimestamp(ps, 23, now)`。
  追加在**最后**可以避免现有 1–21 号参数下标全部错位。

- **Linux**：`process_logs.py` 也已产出 `client_id`（第 92 行），但 `LINUX_COLUMNS`
  里没有它，所以被丢掉了。需要在 `LINUX_COLUMNS` 的 7 个列表中**各追加两项**
  `"source_client_id"`、`"ingested_at"`。

  ⚠️ **一个容易踩的坑**：`linuxSetter` 取的是 `normalized(record)`，
  而 `normalized()` 返回的是 `record["normalized"]` 这个**内层** map，
  `client_id` 在外层，直接加列会取到 `null`。改法：

  ```java
  private Map<String, Object> normalized(Map<String, Object> record) {
      Object value = record.get("normalized");
      Map<String, Object> result = new LinkedHashMap<>();
      if (value instanceof Map<?, ?> map) {
          map.forEach((key, item) -> result.put(String.valueOf(key), item));
      } else {
          result.putAll(record);
      }
      // 采集元数据在归一化结构的外层，必须额外带进来
      result.put("client_id", record.get("client_id"));
      return result;
  }
  ```

  `setField` 里 `source_client_id` 会走 `else` 分支 `setString`，无需改动；
  `ingested_at` 需要走 `setTimestamp`，在 `setField` 的
  `if (field.equals("event_time"))` 里改成
  `if (field.equals("event_time") || field.equals("ingested_at"))`。

**`ingested_at` 用 UTC 显式写入**（重要）：

```java
setTimestamp(ps, index, LocalDateTime.ofInstant(Instant.now(), ZoneOffset.UTC));
// 或直接 repurpose 现有的 setTimestamp 签名
```

**为什么不用 Windows 表已有的 `imported_at`**：它是
`TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`，MySQL 会按会话时区做转换，
而你们的 JDBC URL 写的是 `serverTimezone=Asia/Shanghai`，Linux 侧是 `DATETIME` 裸值。
两种列型和 `UTC_TIMESTAMP()` 混用会**差 8 小时**，导致"近 5 分钟"算错。
统一新增一个显式 UTC 的 `DATETIME(6)` 列最省事，`imported_at` 原样保留不动。

**第二步**：每分钟聚合一次，写回 `collector_client`。
新增 `scheduler/LogMetricsScheduler.java`：

```java
@Component
@Slf4j
public class LogMetricsScheduler {

    /** 12 张表跨两个库 UNION，按 client_id 聚合近 5 分钟条数与最后日志时间 */
    private static final String AGGREGATE = """
            SELECT t.source_client_id AS client_id,
                   MAX(t.ingested_at)  AS last_log_at,
                   COUNT(*)            AS log_count
            FROM (
                SELECT source_client_id, ingested_at FROM `windows_logs`.`application_logs`
                UNION ALL SELECT source_client_id, ingested_at FROM `windows_logs`.`security_logs`
                UNION ALL SELECT source_client_id, ingested_at FROM `windows_logs`.`setup_logs`
                UNION ALL SELECT source_client_id, ingested_at FROM `windows_logs`.`system_logs`
                UNION ALL SELECT source_client_id, ingested_at FROM `windows_logs`.`forwardedevents_logs`
                UNION ALL SELECT source_client_id, ingested_at FROM `log-linux`.`authentication_session`
                UNION ALL SELECT source_client_id, ingested_at FROM `log-linux`.`account_security_change`
                UNION ALL SELECT source_client_id, ingested_at FROM `log-linux`.`process_command_execution`
                UNION ALL SELECT source_client_id, ingested_at FROM `log-linux`.`file_object_access`
                UNION ALL SELECT source_client_id, ingested_at FROM `log-linux`.`network_ipc_communication`
                UNION ALL SELECT source_client_id, ingested_at FROM `log-linux`.`system_service_audit_lifecycle`
                UNION ALL SELECT source_client_id, ingested_at FROM `log-linux`.`security_policy_config_change`
            ) t
            WHERE t.source_client_id IS NOT NULL
              AND t.ingested_at >= UTC_TIMESTAMP(6) - INTERVAL 5 MINUTE
            GROUP BY t.source_client_id
            """;

    @Scheduled(cron = "0 * * * * *")   // 每分钟一次
    @Transactional
    public void refreshLogMetrics() {
        // 1) 先把所有客户端清零，再按聚合结果回填，避免旧数据残留
        jdbcTemplate.update("UPDATE `log_monitor`.`collector_client` SET logs_last_5m = 0, log_status = 'NO_LOG' WHERE log_status <> 'INTERRUPTED'");
        // 2) 回填：有日志 → NORMAL
        //    UPDATE collector_client c JOIN (聚合) a ON c.client_id = a.client_id
        //    SET c.logs_last_5m = a.log_count, c.last_log_at = a.last_log_at, c.log_status = 'NORMAL', c.updated_at = ?
        // 3) 若已落库 buffered_chunks / output_healthy，再按 3.3 覆盖 BACKLOG / INTERRUPTED
    }
}
```

**为什么必须定时聚合**：前端每 5 秒刷新一次，如果每次刷新都去 `COUNT(*)` 12 张表，
生产库会被打垮。每分钟一次、把结果写回 `collector_client`，页面查询就是单表读取。

**数据来源建议**：建一个视图，把 12 张表的采集元数据统一起来（见 6.3），
然后每个平台取最近若干条：

```sql
-- Windows 侧示例（5 张表同样结构，UNION ALL 起来）
( SELECT `time_created` AS log_time, 'info' AS level, 'windows/security' AS category,
         `channel` AS source,
         CONCAT('EventID=', COALESCE(`event_id`,''), ' Level=', COALESCE(`level`,''),
                ' Provider=', COALESCE(`provider_name`,'')) AS message
    FROM `windows_logs`.`security_logs`
   WHERE `source_client_id` = ?
   ORDER BY `ingested_at` DESC LIMIT 20 )
```

都能识别；上面的字段之外的会被忽略，缺字段时该行退化为原始 JSON 展示；
空数组时页面显示「该客户端最近没有日志记录」。

```json
{
  "code": 0,
  "message": "success",
  "data": [
    {
      "snapshotTime": "2026-10-07T00:05:00.000Z",
      "totalCount": 10,
      "onlineCount": 8,
      "delayedCount": 2,
      "offlineCount": 0
    }
  ]
}
```

数据来自 `client_status_snapshot`（每分钟一条，24 小时 = 1440 条，前端直接能画）：

```sql
SELECT snapshot_time, total_count, online_count, delayed_count, offline_count
  FROM `log_monitor`.`client_status_snapshot`
 WHERE snapshot_time >= UTC_TIMESTAMP(6) - INTERVAL ? HOUR
 ORDER BY snapshot_time ASC
```

数组为空时前端显示「暂无趋势数据」，不会报错。

## 6. 建表与字段变更 SQL

### 6.1 新增监控库与两张表

建议新增独立库 `log_monitor`（`application.yml` 加一项，沿用现有前缀风格）：

```yaml
log-database:
  windows: windows_logs
  linux: log-linux
  monitor: log_monitor     # 新增
```

> 也可以把这两张表放进 `log-linux`，只要 SQL 里的库名跟着改。
> 注意 JDBC URL 没有默认库，**所有 SQL 必须写全限定名**（`LogRepository.qualified()` 已是这个风格）。

```sql
CREATE DATABASE IF NOT EXISTS `log_monitor`
  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS `log_monitor`.`collector_client` (
    client_id               VARCHAR(64)  NOT NULL,
    ip_address              VARCHAR(45)  NOT NULL,
    server_name             VARCHAR(128) NOT NULL,
    os_type                 VARCHAR(16)  NOT NULL,
    os_version              VARCHAR(128) NOT NULL,
    fluent_bit_version      VARCHAR(32)  NULL,
    heartbeat_interval_sec  INT          NOT NULL DEFAULT 5,
    last_heartbeat_at       DATETIME(6)  NOT NULL,
    last_log_at             DATETIME(6)  NULL,
    logs_last_5m            BIGINT       NOT NULL DEFAULT 0,
    log_status              VARCHAR(20)  NOT NULL DEFAULT 'NO_LOG',
    buffered_chunks         INT          NOT NULL DEFAULT 0,
    output_healthy          TINYINT(1)   NOT NULL DEFAULT 1,
    cpu_usage_percent       DECIMAL(5,1) NULL,
    memory_usage_mb         INT          NULL,
    created_at              DATETIME(6)  NOT NULL,
    updated_at              DATETIME(6)  NOT NULL,
    PRIMARY KEY (client_id),
    KEY idx_last_heartbeat (last_heartbeat_at),
    KEY idx_os_type (os_type),
    KEY idx_log_status (log_status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE IF NOT EXISTS `log_monitor`.`client_status_snapshot` (
    id            BIGINT      NOT NULL AUTO_INCREMENT,
    snapshot_time DATETIME(6) NOT NULL,
    total_count   INT         NOT NULL,
    online_count  INT         NOT NULL,
    delayed_count INT         NOT NULL,
    offline_count INT         NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_snapshot_time (snapshot_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

⚠️ **`ip_address` 故意没有设唯一索引**（指南里有 `uk_client_ip`）。
因为落库用的是 `ON DUPLICATE KEY UPDATE`：如果两台客户端经过 NAT 后来源 IP 相同，
唯一索引会让第二条记录**更新到别人的行上**。`client_id` 是主键，已经能保证唯一性。

### 6.2 给 12 张日志表补采集元数据

**Windows 5 张**：`application_logs`、`security_logs`、`setup_logs`、`system_logs`、`forwardedevents_logs`（库 `windows_logs`）

```sql
ALTER TABLE `windows_logs`.`application_logs`
  ADD COLUMN `source_client_id` VARCHAR(64)  NULL COMMENT '采集端 client_id',
  ADD COLUMN `ingested_at`      DATETIME(6)  NULL COMMENT '汇聚端入库时间(UTC)',
  ADD KEY `idx_client_ingested` (`source_client_id`, `ingested_at`);
```

**Linux 7 张**：`authentication_session`、`account_security_change`、
`process_command_execution`、`file_object_access`、`network_ipc_communication`、
`system_service_audit_lifecycle`、`security_policy_config_change`（库 `log-linux`）

```sql
ALTER TABLE `log-linux`.`authentication_session`
  ADD COLUMN `source_client_id` VARCHAR(64)  NULL COMMENT '采集端 client_id',
  ADD COLUMN `ingested_at`      DATETIME(6)  NULL COMMENT '汇聚端入库时间(UTC)',
  ADD KEY `idx_client_ingested` (`source_client_id`, `ingested_at`);
```

> `log-linux` 带连字符，**必须用反引号**（`LogRepository.qualified()` 已经处理了）。

**历史数据可选回填（仅 Windows）**：老数据的 `client_id` 被拼进了 `source_file`，
形如 `fluent-bit://fb-win-001/Security`，可以反解出来：

```sql
UPDATE `windows_logs`.`security_logs`
   SET `source_client_id` = SUBSTRING_INDEX(SUBSTRING_INDEX(`source_file`, '/', 3), '/', -1)
 WHERE `source_file` LIKE 'fluent-bit://%'
   AND `source_client_id` IS NULL;
```

Linux 的历史数据没有留下 `client_id`，只能留空（按 `NULL` 处理，不计入任何客户端）。

**建表方式**：项目里没有 Flyway，建议把上面的 SQL 存成
`src/main/resources/db/migration/` 或 `docs/sql/` 下的脚本，手工执行并在团队内留档；
`ddl-auto` 那套在这里不适用（也没引 JPA）。

## 7. 前端已有的容错

| 情况 | 前端行为 |
|---|---|
| 超时（> 8 秒）/ 后端未启动 | 顶部错误提示条 + 重试按钮 |
| 某次刷新失败 | **保留上一份成功数据**，显示「最近成功刷新时间」，不清空页面 |
| 连续失败 ≥ 2 次 | 提示升级为「已连续 N 次刷新失败」，恢复后自动继续 |
| `code != 0` | 直接展示后端返回的 `message` |
| 详情接口 404/失败 | 弹窗退回显示列表行已有字段 |
| 日志为空 | 显示「该客户端最近没有日志记录」 |
| 趋势为空 | 显示「暂无趋势数据」 |
| `cpuUsagePercent` / `memoryUsageMb` 缺失 | 详情弹窗两行显示 `-` |
| 未知枚举值 | 显示「未知」，不报错 |
| 只有 `NORMAL`/`NO_LOG` 两种日志状态 | 另两种的样式已写好，后端一旦返回就自动生效 |

**CORS**：开发环境走 Vite 代理（`5173` → `8080`），不需要配。
只有当前端产物直接对着 `8080` 打开时才需要，加一段即可：

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("http://localhost:5173", "http://127.0.0.1:5173")
                .allowedMethods("GET", "POST")
                .allowedHeaders("Content-Type", "Authorization");
    }
}
```

不要用 `allowedOrigins("*")`。

## 8. 联调自测

后端起来后（默认 8080），先造心跳数据。**注意现有协议是数组体、单数路径**：

```bash
curl -X POST http://127.0.0.1:8080/api/v1/heartbeat \
```

> `[{"client_id":"fb-linux-001","os_type":"Linux","os_version":"UOS Server 20 (1060e)","fluent_bit_version":"3.0.7"}]`

再验 5 个查询接口：

```bash

curl "http://127.0.0.1:8080/api/v1/monitor/clients?page=1&size=20"
curl "http://127.0.0.1:8080/api/v1/monitor/clients/fb-linux-001"

curl "http://127.0.0.1:8080/api/v1/monitor/trend?hours=24"
```

最后打开前端 `http://127.0.0.1:5173`（后端端口若不是 8080，
改 `D:\log-Frontend\.env.development` 的 `VITE_PROXY_TARGET`）。

**停止发送心跳后的预期时间线**（以最后一次成功落库为起点）：

| 时间 | 该客户端应变为 |
|---|---|
| 心跳持续发送 | `ONLINE`（`heartbeatDelaySec` 0–5） |
| 停发第 11 秒 | `DELAYED` |
| 停发第 31 秒 | `OFFLINE`，且**仍然出现在列表里**（这正是必须落库、不能再依赖内存表的原因） |

边界必须是：`age <= 10` → ONLINE，`10 < age <= 30` → DELAYED，`age > 30` → OFFLINE。
建议对 0 / 10 / 11 / 30 / 31 秒写单元测试。

## 10. 顺带发现的几个问题（与本文档无关但建议处理）

1. **数据库密码明文入库**：`src/main/resources/application.yml` 第 8 行
   `password: mysql_YbJWfE`，且 git 工作区干净说明**已经提交**；
   `src/main/python/windows/config.py` 第 22 行把同一个密码写成了默认值。
   建议改成 `${MYSQL_PASSWORD}` 环境变量，并考虑轮换密码、换掉 root 账号。

2. **`HeartbeatWatchdog` 的注释与代码不一致**：注释写「每 5 秒巡检一次」，
   实际是 `@Scheduled(fixedDelay = 3 * 1000)`（3 秒）；阈值注释写 15 秒，代码也是 15 秒，
   与页面要用的 10/30 秒是两套值——这是有意的（告警更敏感），但建议在注释里写清楚。

3. **`clientLastSeenMap` 是 controller 里的 `public static` 字段**，
   被 scheduler 直接读写。落库之后这个表只服务告警，
   可以考虑挪到一个 `HeartbeatRegistry` 组件里，避免 controller 与 scheduler 互相耦合。

4. **`LogController` 收到非法 JSON 时**：`PythonLogProcessor.process` 会抛
   `LogProcessingException`，当前没有 `@ExceptionHandler`，客户端拿到的是 Spring 默认 500。
   `openspec/specs/log-ingestion/spec.md` 里写的是**期望 400**，可以顺手补上。
