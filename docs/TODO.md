## 高优先级

| 问题 | 影响 | 建议方案 | 验收标准 |
|---|---|---|---|
| 数据库默认 root 凭据写在代码中 | 凭据泄露和过度授权风险 | 轮换密码、使用最小权限账号、部署时强制环境注入；评估移除敏感默认值 | 仓库不含有效密码；四个库权限按读写需求拆分；缺少配置时有清晰错误 |
| 既有日志表和存证表没有仓库内正式 DDL/迁移 | 无法可靠重建环境，字段漂移只能运行时报错 | 从真实库导出 DDL，审查后建立 Alembic 或版本化 SQL；禁止直接改线上表 | 新环境可按文档重建；迁移可追踪、可回滚；`DATABASE.md` 与 DDL 一致 |
| 写入和查询接口没有认证授权 | 任意可达主机可写日志、读数据和导出 | 明确内网信任边界，增加采集端凭据与管理员认证/授权 | 未授权请求被拒绝；采集端和浏览器权限分离；密钥可轮换 |
| 新增的 `POST /api/v1/admin/update` 无鉴权，任何可达者都能触发「停服 + 覆盖代码 + 重启」 | 暴露到不可信网络时，等于把线上重部署权限交给访问者 | 共享令牌或来源 IP 白名单并限流；密钥仅服务端持有、不写进代码 | 未授权请求被拒绝；合法触发仍可用；密钥可轮换 |

## 中优先级

| 问题 | 影响 | 建议方案 | 验收标准 |
|---|---|---|---|
| 类别查询只校验字符，不校验类别白名单；未知平台默认按 Linux | 可探测同库其他表，错误语义不清晰 | 强制类别属于 catalog、平台只允许 Linux/Windows | 非法平台或未知类别返回明确 4xx，不能查询 catalog 外表名 |
| `monitor/clients/{client_id}/logs` 未按客户端过滤 | 接口名与实际结果不一致，可能误导排障 | 日志表增加可靠来源字段并建立索引，再按 `client_id` 查询 | 只返回目标客户端日志；无关联时返回空列表并有文档说明 |
| 存证功能只有最多 1000 条兼容读取 | 故障被伪装为空数据，统计/导出不完整 | **已修复（2026-10-11）**：存证改读真实 `log_hash` 表，数据库侧真分页，新增归档导出 | 已完成；遗留的「存证逐条校验接口」见本表下一行 |
| 存证只有入库时算出的摘要，没有逐条校验接口 | 页面上无法验证某条存证是否被篡改，只能在 MySQL 里手工复算 | **已修复（2026-10-13）**：`summary`/`list`/`export` 均在 SQL 侧逐条复算并给出 `verify_status`，页面有校验列、异常筛选与告警条 | 已完成 |
| Windows 日志全部没有存证（载荷无 `log` 字段，逐条被静默跳过） | 2026-10-15 核验：441,408 行 Windows 业务数据对应 0 条存证，占「日志总量 − 存证总量」缺口的 65.8% | **已修复（2026-10-15）**：`hashing.evidence_input` 按平台分流，Windows 改用整条记录的规范化 JSON 做存证原文（ADR-018） | 已完成；新增 Windows 存证逐条出现，`platform='windows'` 计数开始增长 |
| Windows 存证只覆盖「服务端收到的 JSON」，不覆盖采集端字节流 | 键序/空白/数字字面量/重复键在 FastAPI 反序列化时已定型，无法证明采集端到服务端之间未被改动 | 改采集端 Fluent Bit 输出，让 winlog 记录自带 `log` 字段（届时需决定新旧两种 Windows 存证口径如何共存，见 ADR-018 的兼容性风险） | 新入库的 Windows 存证原文为采集端字节原文，且能与 `raw-logs.log` 样例逐字节对上 |
| 规范化 JSON 的序列化参数是哈希口径的一部分 | 改 `sort_keys`/`separators`/`ensure_ascii` 任一项，会让**已写入的全部 Windows 存证**被判 `HASH_MISMATCH`（历史数据瞬间"看起来被篡改"） | 已由 `tests/test_hashing.py` 锁住；若将来必须调整，需按平台+时间做双口径校验，不能一刀切 | 任何序列化参数变更都有对应测试失败提示 |
| 「日志总量」与「存证总数」并排展示但口径不同 | 2026-10-15 就是因此被当成"数据丢了"来排查。存证功能 2026-10-11 才上线，Linux 侧约 229,285 行历史数据永远不会有存证，两个数短期内不可能相等 | 存证总览按平台拆分并显示「应存证数 / 覆盖率」，或在两个指标上标注统计口径与存证功能启用时间 | 页面上能直接看出"差额是历史基线"而不是"在漏数据" |
| 摘要无法防伪造：`sha256(内容)` 只证明「原文与摘要自洽」，能写库的人可造出两者都自洽的假记录 | 拿到库权限者可伪造存证且检测不出来（2026-10-13 实测确认该边界） | 摘要改为 HMAC-SHA256（密钥仅服务端持有）或对存证行签名；或把摘要同步到客户端/外部不可篡改存储做交叉校验 | 伪造的自洽记录能被检出；密钥可轮换且不以明文落库 |
| 逐条校验是每次请求的整表 SHA-256 扫描 | 表增长到百万级后 `summary` 会明显变慢（万级约 0.2 秒） | 改为增量校验（记录上次位点，只校验新增/变更行）或后台异步任务并缓存结果 | 校验耗时与表总量解耦；页面响应不受校验规模拖累 |
| 存证删除不可逆，仅有台账留痕，且归档 CSV 无异地备份 | 归档文件损坏或误删后无法恢复原始日志 | 为归档目录增加备份/异地同步；补充归档失败告警与多实例互斥 | 归档文件有备份；同一环境不重复归档；失败可告警 |
| 归档 CSV 未做公式注入防护，且一次把待归档行读进内存 | 打开不可信原文有风险，大表归档占用内存 | 对 `= + - @` 前缀转义；改为边查边写而非一次性取行 | 危险前缀已转义；内存占用与行数解耦 |
| 缺少统一错误模型和可观测指标 | 页面吞错，运维难定位 SQL/采集失败 | 定义统一错误响应与 request ID，补充采集成功/失败的指标与告警（`print` 已改为 `logger`，采集失败已有逐条 `errors` 明细） | 4xx/5xx 格式一致；持久化失败可检索并告警；敏感信息不出响应 |
| 概览每 2 秒对 12 张表做 `COUNT(*)` | 单次实测 286–497 ms，持续轮询会一直占着数据库与线程池；多个标签页会成倍放大 | 按只读的 `旧前端/docs/` 契约建议改为**服务端聚合 + 缓存**（后台每分钟（或可配置）算一次，接口读内存缓存），前端仍可 2 秒轮询。**2026-10-13 部分缓解**：新图表用的 `/logs/trend`、`/logs/stats` 已走 `metrics.py` 的进程内 TTL 缓存（命中 228 ms → 10 ms），`/logs/monitor/history` 完全不查库；**`/api/v1/logs/summary` 本身仍未加缓存**，仍是最重的一条持续开销 | `/api/v1/logs/summary` 也变为毫秒级且不再每次扫表；缓存时间戳可在响应中看到 |
| 心跳历史只存在进程内存里，重启即清零 | 延迟趋势图在服务重启后从空白重新累积；多 worker 下每个进程只有自己巡检到的那一段 | 明确这是「排障用短期视图」的口径（ADR-017）；若确需跨重启保留，再新增心跳历史表 + 保留期清理（需要 DDL 变更与单独授权） | 页面在空历史时明确显示「进程刚重启、历史已清零」而不是报错或假装没有心跳；升级为表后重启不丢历史 |
| CSV 导出未防公式注入且一次性装入内存 | 打开不可信字段有风险，大结果集占用内存 | 对危险前缀转义，改为流式/异步导出并限制范围 | `= + - @` 开头字段安全；大结果集内存稳定；响应仍带 UTF-8 BOM |
| WebSocket 缺少鉴权，且连接集合仅在进程内 | 任意可达主机可订阅全量客户端状态；多实例下各实例广播不一致 | 增加连接鉴权；引入 Redis/消息代理等共享消息层 | 未授权连接被拒绝；任一实例接收心跳后所有实例订阅者得到一致快照 |
| 服务端更新脚本失败无告警，`pip install` 失败仍继续启动 | 无人值守时更新中断只在 `/var/log/log-fusion-update.log` 可见；依赖缺失会以启动失败收场 | 更新成功/失败写入可观测通道（邮件/webhook/日志告警），或在 `/health` 暴露「最近一次更新结果」 | 更新结果可被监控采集；失败能触发告警 |
| 原地更新（ADR-020）假定「服务器只拉取、不改代码」，且不校验提交来源 | 若有人在服务器上直接改已跟踪文件，`git reset --hard` 会静默覆盖（仅留 `/root/lf-keep/pre-update-*.patch`）；远端分支被改写或推到一半也能被拉下来，没有校验（签名/哈希/CI 门禁） | 服务器侧只读约定写进运维文档并定期审计；后续可加提交签名或部署前跑一遍测试作为门禁 | 服务器上出现本地改动会被显式告警；部署内容可追溯到受信任的提交 |

| 问题 | 影响 | 建议方案 | 验收标准 |

## 技术债

| 问题 | 影响 | 建议方案 | 验收标准 |
|---|---|---|---|
| 自动化测试只到单元/契约层，且没有 lint / typecheck | 真实库交互（DDL 差异、SQL 方言、WebSocket 端到端）仍依赖人工回归 | 已在 `tests/` 建立不连库的 pytest 契约测试；后续补 lint/typecheck、真实库集成测试与 CI | 已有用例可重复运行且不连接数据库；再补齐集成层与静态检查 |
| `client_status` 用 `create_all()` 自动建表，没有版本迁移 | 模型升级无法安全演进 | 将表纳入迁移，启动仅校验或由部署阶段迁移 | 升级路径可审查，应用账号无需 DDL 权限 |
| 同步 SQL、异步路由和线程切换混用 | 容量和超时行为难预测 | 建立连接池/线程池容量基线，统一数据库访问策略 | 压测下无明显线程饥饿，超时和连接池指标可见 |
| 心跳请求缺少严格 Pydantic 模型和字段边界 | 非法类型可能转成 503 或产生脏数据 | 定义请求模型、长度/范围限制和兼容别名 | 非法输入返回可读 422/400；合法旧字段继续兼容 |
| 图表聚合接口没有「缓存与真实数据的偏差」指标 | 只知道缓存了多久，不知道一次聚合扫描了多少行、花了多久 | 在聚合处记录耗时/行数（logger 或 `/health` 扩展），供容量评估 | 能看到趋势/排行查询的耗时分布与缓存命中率 |
| 时间桶查询依赖 `event_time`/`time_created` 索引，新增表可能漏建 | 缺索引时 30 天窗口会退化成全表扫描，拖慢整个库 | 新增日志表时同步补 `idx_event_time`/`idx_time_created`；纳入建表检查清单（2026-10-13 已只读核验现有 12 张表齐备） | 新表建表脚本带时间列索引；有核验 SQL 可复查 |
| `event_time`/`time_created` 索引已核验但**未纳入仓库内 DDL** | 换环境重建时索引信息仍只存在于文档结论里 | 与「日志表缺正式 DDL」合并处理，把索引一并纳入版本化 DDL（需单独授权的数据库变更） | 新环境按仓库内 DDL 重建后，趋势查询仍走索引 |

## 安全产品接入跟踪（2026-10-16）

- 已完成：三张日志表与同步表实际建表、归一化与事务断点、时间拆分、增量后台、只读 API 和前端 10 秒更新。用户确认历史量足够，当前默认开启仅实时采集。
- 不再要求全量历史验收：用户确认已有数据足够，剩余历史任务停止并保留；本次验收改为启动仅查近期、不会自动续跑旧队列。不要把 stopped 标成完整历史已完成。
- 待长期验证：六百万量级实际耗时/磁盘容量与保留策略；超过回看窗口的迟到数据；单秒超过 API 限额时须增加已验证的额外分片条件。不要用估计总数声称这些边界已覆盖。
