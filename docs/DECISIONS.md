## ADR-001：当前实现使用 FastAPI 与服务端渲染

- 状态：已采用
- 背景：仓库保留旧 Vue/Spring Boot 实现，但现行入口位于 `backend/app/main.py`。
- 决策：使用 FastAPI 提供 API、SSE、WebSocket 和 Jinja2 首页；`旧前端/`、`旧后端/` 只读保留。
- 原因：当前代码已经完成该迁移；选择该技术栈的原始业务理由待确认。
- 后果：开发应围绕 `backend/` 与 `frontend/`，不得继续在遗留工程实现新功能。
- 后续：`python/` 过期路径引用已清理完毕（活代码、规则文件、`docs/` 和启动脚本均指向 `backend/`），仅 `旧后端/`、`旧前端/docs/` 历史材料保留原路径。

## ADR-002：浏览器界面无构建步骤

- 状态：已采用（2026-10-10 修订依赖加载方式，见 ADR-011）
- 背景：当前页面由 Jinja2 输出，交互和图表依赖浏览器库。
- 决策：仍然没有前端构建步骤；Bootstrap、HTMX、Alpine.js、ECharts 改为从 `frontend/vendor/` 自托管，本地只维护模板和 `frontend/app.js`。
- 原因：降低开发期前端构建复杂度；原始决策记录代码中未发现。
- 后果：部署简单且断网可用；代价是仓库内多出约 1.36 MB 第三方文件，升级需手工替换并同步模板引用。
- 后续：升级依赖时按 `frontend/vendor/README.md` 的流程新增版本化文件。

## ADR-003：按用途拆分三个 MySQL 逻辑库

- 状态：已采用（2026-10-11 更新：库数量由 3 个增至 4 个）
- 背景：Linux 与 Windows 历史表结构不同，平台心跳需要独立状态表。
- 决策：`linux_logs` 保存 7 类 Linux 表，`windows_logs` 保存 5 类 Windows 表，`log_fusion` 保存 `client_status` 与 `archive_log`，`log_hash` 保存原始日志存证（2026-10-11 新增）；应用为四个库创建独立 SQLAlchemy Engine。
- 原因：兼容既有表和独立的数据模型；存证数据与业务日志的生命周期、删除策略完全不同，放在独立库避免归档删除影响业务查询。
- 后果：跨库最近日志在 Python 中合并，无法使用单一事务覆盖四个库；配置和健康检查必须同时考虑四个连接。
- 后续：核验正式 DDL、索引、账号权限和备份策略。

## ADR-004：心跳持久化，实时连接保持进程内

- 状态：已采用
- 背景：客户端状态需要跨服务重启保留，同时浏览器需要实时收到快照。
- 决策：心跳以 MySQL upsert 写入 `client_status`；后台每 5 秒重算状态；WebSocket 连接集合和日志 SSE `asyncio.Queue` 保留在单进程内存。
- 原因：持久化状态便于恢复，进程内广播实现简单。
- 后果：客户端记录可跨重启保留，但重启会断开实时连接并清空未消费日志事件；多 worker 之间不会共享连接或队列。
- 后续：在引入多实例前改用 Redis、消息代理或数据库事件表，并实现真正的多订阅者广播。

## ADR-005：兼容既有日志表，不自动管理其结构

- 状态：已采用
- 背景：日志库已有分类表，当前仓库没有这些表的正式迁移脚本。
- 决策：应用通过文本 SQL 直接读写既有 Linux/Windows 表，只对白名单类别选择写入表；启动时仅通过 ORM 自动创建 `client_status`。
- 原因：避免在重构期直接改动历史日志表；完整原因待确认。
- 后果：代码与实际 DDL 漂移时会在运行期失败；部分查询假设的字段不一定存在；不能从仓库独立重建日志库。
- 后续：导出并审查真实 DDL，建立 Alembic 或受控 SQL 迁移和兼容性检查。

## ADR-006：采集持久化失败时返回可观察的降级结果

- 状态：已采用
- 背景：旧表可能存在字段差异，但实时页面仍希望看到采集事件。
- 决策：`POST /api/v1/logs/{platform}` 捕获数据库写入异常，返回 HTTP 200 与 `persisted: false`，随后仍把摘要放入 SSE 队列。
- 原因：维持采集端兼容并让实时通道继续工作。
- 后果：HTTP 成功不等同于数据已持久化，调用方必须检查 `persisted`；当前仅打印失败信息，没有持久化失败队列或告警。
- 后续：增加结构化日志、失败指标、重试/死信机制，并评估是否需要更明确的状态码。

## ADR-008：PowerShell 脚本使用 UTF-8 with BOM

- 状态：已采用
- 背景：Windows PowerShell 5.1 对无 BOM UTF-8 中文脚本可能按系统代码页解析。
- 决策：所有 `.ps1` 保持 UTF-8 with BOM；涉及中文路径时使用 `-LiteralPath`。
- 原因：避免中文标点或字符串产生解析错误。
- 后果：编辑脚本后必须检查文件头 `EF BB BF`，并避免无意义的编码转换。
- 后续：将 BOM 检查加入自动化验证脚本。

## ADR-009：心跳快照按固定周期无条件广播

- 状态：已采用
- 背景：浏览器需要持续的心跳状态；同时中间代理/网关可能静默断开空闲 WebSocket，而前端仅靠“消息内容变化”无法区分“状态没变”和“连接已假死”。
- 决策：`_status_watchdog()` 每 5 秒重算全部客户端状态，状态变化时才 `UPDATE` 数据库，但每轮都无条件广播一次完整快照；前端超过 20 秒未收到任何消息即主动关闭连接并按指数退避重连。
- 原因：用周期快照同时充当应用层保活与前端活性判据，不必额外定义 ping/pong 协议。
- 后果：连接空闲时仍保持固定消息量（每客户端数×每 5 秒一帧完整快照）；多实例部署时每个实例各自广播，连接与队列仍不共享。
- 后续：多实例化时引入共享消息层，并评估客户端数量增长后的快照体积与广播开销。

## ADR-010：分类列表与 CSV 导出使用不同的单次取数上限

- 状态：已采用
- 背景：分类列表接口把单次条数限制在 100，CSV 导出复用同一查询函数，导致导出 `size` 传 1000/10000 时被静默截断为 100 行，接口参数语义与文档不符。
- 决策：`query_category()` 增加 `size_cap` 参数；列表接口保持 100，导出显式传 10000。
- 原因：不改变列表接口已有的分页边界，同时让导出接口的 `size` 参数真实生效。
- 后果：单次导出最多 10000 行，且在内存一次性构造 CSV，仍需公式注入防护与流式/异步导出。
- 后续：见 `TODO.md` 中 CSV 导出相关条目。

## ADR-011：前端依赖由 CDN 改为本地自托管

- 状态：已采用
- 背景：本机 DNS 被代理接管，`cdn.jsdelivr.net` 解析为 `198.18.0.x` 的 fake-IP，四个前端库的请求要绕经代理 TUN，首屏多出数秒等待；隔离网或断网环境下则完全加载不出来。
- 决策：把 Bootstrap 5.3.3、HTMX 2.0.4、Alpine.js 3.14.8、ECharts 5.5.1 下载到 `frontend/vendor/`（文件名内嵌版本号），模板只引用 `/static/vendor/...`；`/static/vendor/*` 允许长期缓存，应用自身资源（`app.js` 等）继续禁用缓存。
- 原因：本地静态资源没有 DNS 与代理环节，四个库合计加载从约 2 秒降到约 0.1 秒，并且满足离线部署。
- 后果：失去“改 URL 即升级”的便利，升级需重新下载文件并同步模板；仓库体积增加约 1.36 MB。
- 后续：按 `frontend/vendor/README.md` 的流程升级；评估子资源完整性校验与 ECharts 体积裁剪。

## ADR-012：前端页面不再订阅 SSE，实时更新改由 WebSocket 承担

- 状态：已采用
- 背景：浏览器对同一地址的 HTTP/1.1 连接上限是 6 条。前端每个页面原本占用 1 条日志 SSE + 1 条心跳 WebSocket，刷新与多标签会让 SSE 累积（实测服务端 `sse_clients` 达到 6），把所有额度占满，导致包括自动刷新在内的所有 REST 请求永久排队：页面转圈、心跳页无数据，而服务端接口仍是毫秒级。
- 决策：前端移除 `EventSource`，只保留 1 条心跳 WebSocket 作为长连接；心跳状态由 WebSocket 每 5 秒推送的快照更新，概览每 10 秒轮询 REST，日志/存证页各 15 秒刷新，WebSocket 断开时退化为 5 秒轮询。`/api/v1/logs/stream` 接口保留给外部消费方。
- 2026-10-13 调整：概览统计改为每 **2 秒**刷新（产品要求更实时），并加两条保护——只在概览页可见时轮询、上一条未返回就跳过（`summaryBusy`），数据未变化则不重画环形图。注意 `/api/v1/logs/summary` 是 12 张表的 `COUNT(*)`（实测单次 286–497 ms），因此「更快的刷新」是持续数据库开销，缓存/定时聚合方案见 `TODO.md`。
- 原因：WebSocket 不占用 HTTP 连接额度，REST 请求不再被长连接挤掉；同时消除“每条日志事件触发一次 12 张表 `COUNT(*)`”的重复统计。
- 后果：概览统计从“日志事件驱动”变为 10 秒定时刷新，实时性略降；运维需要知道 SSE 与 WebSocket 是两套独立通道。
- 后续：若确需日志事件级的实时推送，应扩展 WebSocket 消息类型，而不是重新引入每页一条 SSE。

## ADR-013：采集解析独立成层，时间统一归一化为 UTC datetime

- 状态：已采用
- 背景：采集端送来的是原始记录（Fluent Bit Linux JSON 里的 syslog/auditd 文本行、Windows winlog JSON），入库却需要分类表的类型化字段。此前解析与入库混在 `main.py`，时间字段以原始字符串直接写 `datetime` 列，导致每条记录都报 `(1292, "Incorrect datetime value")`，而失败只以 `print` 记录，无法判断是解析还是入库的问题。
- 决策：新增 `backend/app/parsers.py` 作为纯函数解析层（逻辑参考只读的 `旧后端/log-backend/src/main/python/`）：时间统一解析为 UTC naive `datetime`；按 `catalog.LINUX_TABLE_FIELDS` / `catalog.WINDOWS_TABLE_FIELDS` 裁剪行并做类型归一化；解析与入库分离，接口按 `parse` / `insert` 分阶段返回失败明细。
- 原因：MySQL `datetime` 不接受 ISO `Z` 或带 `+0800` 的字符串；整型列写空字符串报 1366、超长字符串报 1406、写表里不存在的列报 1054。把这些规则收敛到解析层后可以单测，并让采集端拿到可定位的错误。
- 后果：解析层必须随真实 DDL 变化同步维护（列清单已用 `information_schema` 核验）；未收录的 auditd 类型会被显式报错而不是静默丢弃，需要按需扩充映射表。
- 后续：补充更多 auditd 类型映射、采集失败的重试/死信与指标（见 `TODO.md`）。

## ADR-014：存证归档先导出落盘、再按 id 删除

- 状态：已采用
- 背景：存证表 `log_hash.log_hash` 会持续增长，需要把历史记录导出为 CSV 并从库中删除（自动：3 个日历月之前；手动：选定时间区间）。删除不可逆，一旦「删了但没导出成功」就是永久丢失原始日志。
- 决策：
  1. **先查 id 集合**（受 `ARCHIVE_BATCH_LIMIT` 限制），再按 id 分批取行写 CSV；
  2. 写完后 `flush` + `fsync`，校验文件存在、大小 > 0、行数与 id 数一致；
  3. 只有以上校验全部通过才执行 `DELETE`，且**用明确的 id 列表删除**，不用 `DELETE WHERE created_at < X`；
  4. 时间口径统一用 `created_at`（入库时间），不用 `event_time`；
  5. 每次归档写一条 `log_fusion.archive_log` 台账（含文件路径、行数、删除数、文件 SHA-256）。
- 原因：
  - 用 `created_at` 是因为客户端会补传历史日志，按 `event_time` 会出现「刚入库就被归档」；
  - 用 id 列表而不是时间条件，是因为时间条件会连带删掉归档执行期间新写入、同样满足条件的记录；
  - 台账写失败不影响归档结果（只记日志）：归档本身已完成，把台账故障报成失败会让人误以为数据还在。
- 后果：归档是「至少一次」语义——删除失败会留下重复导出，下次重跑可能产生第二个 CSV，属于可接受的方向（宁可重复导出，不可丢数据）。归档文件永久保留、不自动清理，磁盘容量需自行规划。
- 后续：为归档目录补备份/异地同步、归档失败告警与多实例互斥；归档 CSV 目前未做公式注入防护（见 `TODO.md`）。

## ADR-015：移除 SSE，实时能力统一由 WebSocket 承担

- 状态：已采用（2026-10-13）
- 背景：
  - SSE 通道 `GET /api/v1/logs/stream` 自 ADR-012 之后**已无内置消费方**（前端不再订阅），保留它意味着维护两套实时语义；
  - 它有两个结构性缺陷：① 所有连接共享一个进程内队列，多个订阅者是**竞争消费**而非广播，订阅者各拿到不同事件；
    ② 生产者用等待式 `put()`，队列（上限 1000）满时会**反向阻塞采集请求**；
  - 仓库发展方向是「所有实时同步都走 WebSocket」，而 WebSocket 广播是给每条连接单独发送，天然支持多订阅者，不存在上述两个问题。
- 决策：
  1. 删除 `/api/v1/logs/stream` 路由、`event_queue`、`sse_clients` 计数、`sse-starlette` 依赖，
     以及只为 SSE 存在的 `_summary_from_row`/`_summary_from_raw` 与 `persist_logs()` 的 `summaries` 返回项；
  2. 采集接口不再推送逐条日志事件；页面统一用**定时 REST 刷新**（概览 2 秒、日志/存证页 15 秒）；
  3. `/health` 的 `realtime` 只保留 `ws_clients`（**破坏性变更**，读取 `sse_clients` 的外部监控需同步改）；
  4. **未来所有实时推送都加在 `/ws/client-monitor` 上**，并遵守消息约定：每条消息带 `type` 字段
     （现有心跳快照视为 `"snapshot"`），消费方必须忽略未知 `type`，新增类型不得改变已有字段语义。
- 原因：一个通道、一套语义、一个消费约定，比「按数据类型分协议」更容易维护；WS 的每连接发送也直接消除了
  竞争消费与背压两个缺陷（`docs/TODO.md` 里对应的技术债随之关闭）。
- 后果：
  - 日志事件级实时性不再存在（本来也无人消费）；若将来需要「新日志到达即刷新」，
    按上述约定往 WebSocket 加一条 `type:"log"` 消息即可，**不要重新引入 SSE**；
  - 实时连接集合仍在进程内存：**必须单 worker**，多实例需要共享消息层（Redis 等）才能横向扩展；
  - 浏览器每页只占 1 条长连接（WebSocket 不占 HTTP/1.1 的 6 条额度），这也是当初选择它的原因。
- 后续：为 WebSocket 增加鉴权；需要多实例时引入 Redis 发布订阅并统一 `type` 消息总线。

## ADR-016：图表数据一律由服务端聚合，并在服务端做 TTL 缓存

- 状态：已采用（2026-10-13）
- 背景：
  - 运行概览、心跳监控、日志统计三个页面要新增 10 张实时图表，任何一张图都需要**时间序列**数据，而此前全站 22 条接口只返回「当前时刻快照」，没有任何历史序列；
  - 最直接的替代方案是前端自己缓冲历史（每次轮询把点推进数组），但那样每个标签页各自算一份、刷新即丢、图表口径互不相同，且热力图需要的 7×24 聚合还得在每个浏览器里各算一遍；
  - 同时必须承认代价：12 张表的 `GROUP BY` 比 `COUNT(*)` 更重，而概览已经在每 2 秒做一次 12 表 `COUNT(*)`（实测 286–497 ms）。
- 决策：
  1. 新增三条聚合接口 `GET /api/v1/logs/trend`、`GET /api/v1/logs/stats`、`GET /api/v1/monitor/history`（接口总数 22 → 25），图表数据只从接口取，**前端不维护历史缓冲**；
  2. 趋势与排行在服务端做**进程内 TTL 缓存**（趋势 `1h` 5 秒 / `24h` 15 秒 / `7d`·`30d` 60 秒，排行 60 秒），响应必带 `generatedAt`/`cached`/`ageMs`，让「数据有多新」在页面和排障时都可见；
  3. 刷新节奏不得比原有概览汇总更密：概览趋势 10 秒、心跳历史 10 秒、统计子页 30 秒，且都遵守「当前页可见 + busy 标志防叠加 + 8 秒请求超时」；
  4. **时间桶一律输出 UTC**（`...Z`），本地化只在前端渲染时做——后端做时区转换会把「服务器时区」偷偷写进业务口径；热力图这类需要本地时间的聚合由前端用 `Date` 转换后完成；
  5. 组合出的数据点超过上限（如 `range=30d&bucket=minute` → 4 万多点）在查库前直接返回 400，不给数据库制造无意义负载。
- 原因：口径唯一（所有人都看同一份服务端聚合结果）、代价可控（TTL 缓存把重复轮询挡在数据库之外，实测缓存命中 228 ms → 10 ms）、与既有「单 worker + 进程内状态」的架构约束一致，不引入 Redis 等新依赖。
- 后果：
  - 缓存与心跳历史都在进程内 → **必须单 worker**；多 worker 下每个进程各有一份缓存（结果仍正确，只是各自计时）；
  - 数据新鲜度有上限（最坏情况是 TTL 与轮询间隔之和），页面必须显示这行信息而不是假装实时；
  - 时间桶查询依赖 `event_time`/`time_created` 索引（2026-10-13 只读核验确认已存在），新增表必须补索引；
  - 图表聚合接口查询失败返回 **500**（不降级成「全 0 趋势」），延续「不把故障伪装成没有数据」的既定原则。
- 后续：给 `/api/v1/logs/summary` 本身也加缓存（TODO.md 高优先级技术债）；若将来缓存需要跨实例共享，再引入 Redis。

## ADR-017：心跳历史用进程内环形缓冲，不新增历史表

- 状态：已采用（2026-10-13）
- 背景：心跳页的延迟趋势需要 15 分钟滚动序列。可选方案有三种：① 新增 `client_status_history` 表（或把每次心跳都落库）；② 引入时序库；③ 在已有的 5 秒 watchdog 巡检里顺手采样到内存。
  - 方案①要改 DDL，且心跳当前每客户端每 5 秒一轮，长期落库会持续放大写入量与存储（本项目的 `client_status` 只保留每个客户端的最新一行，正是为了避免这种放大）；
  - 方案②引入新依赖，与「不加依赖、必须单 worker」的现状不符；
  - 方案③零 DDL、零查询，代价仅是重启后历史清零。
- 决策：在 `_status_watchdog`（每 5 秒一轮）里调用 `metrics.record_sample()`，把快照压成一个采样点追加到容量 720 的 `deque`（≈ 1 小时）；`/api/v1/monitor/history` 只读内存，**完全不查库**，进程重启后返回空序列而不是错误。
- 原因：这是唯一能同时满足「不新增表/不新增依赖/不加重数据库负载」的方案；心跳历史是**排障用的短期视图**，1 小时窗口足够，且数据库故障时该接口仍可用（不依赖 MySQL）。
- 后果：
  - **进程重启后历史清零**：页面必须显示「暂无历史采样点」的空态并说明原因，绝不能把「刚重启」表现成「查询失败」或「从来没有心跳」；
  - 多 worker 下每个进程只有自己巡检到的采样点，曲线会缺段（单 worker 是硬约束）；
  - 内存开销约 720 × (客户端数) 的小对象，可忽略；
  - 若将来确实需要跨重启保留，再升级为独立历史表（届时需要 DDL 变更与保留策略），本次刻意不做。
- 后续：可选增强「客户端状态时间线热力图」（client × 时间 的状态色带）已登记在 `TODO.md`。

## ADR-018：Windows 存证原文改用整条记录的规范化 JSON

- 状态：已采用（2026-10-15）
- 背景：存证写入端只认载荷里的 `log` 字段（`hashing.build_evidence_row`），而 Fluent Bit winlog 载荷根本没有 `log`——只有 `TimeGenerated`/`EventID`/`Channel`/`Data` 这类字段（见 `docs/API.md` 的 Windows 样例）。结果是**每一条** Windows 日志都命中「缺少 log 字段」分支被静默跳过存证，但日志照常入库、接口照常返回 200。2026-10-15 只读核验：业务表合计 713,395 行，存证表 42,702 行且 `platform='windows'` 为 **0**；缺口的 65.8%（441,408 行）来自这里。
  - ⚠ 排查过程中一度把「`time_created` 最大值是今天」当成「Windows 仍在实时进数据、缺口每秒扩大」，**这个推论是错的**：`time_created` 是事件在源机器上的时间，不是入库时间，而 Windows 业务表没有 `created_at` 列，无法据此判断最后一次实际入库时刻。核验时刻（2026-10-15 14:47）Windows 三张表已无新增，最后一条事件时间为 `2026-10-15 02:41`（UTC）。**「缺口是否仍在扩大」属待确认**，需查采集端或服务端访问日志才能定论。
- 决策：在 `hashing.evidence_input` 里按平台分流——Linux 继续用 `log` 字段原文（**一字不改**，避免已有的 42,702 条存证被判篡改）；Windows 用 `canonical_json(record)`（`sort_keys=True` + `separators=(",", ":")` + `ensure_ascii=False`）作为存证原文，时间戳按 `WINDOWS_TIMESTAMP_KEYS` 的优先级取原始字符串。
- 备选与否决：
  - ① 只用 `Message`/`Data` 当事件正文：最接近 Linux 的 `log` 语义，但 4672/4624 这类高频事件的 `Message` 常为空或只有参数，会把 `EventID`、`Channel`、`Computer` 这些真正有审计价值的字段排除在存证之外——**否决**。
  - ② 改采集端让 winlog 输出带 `log`：代码零改动且能拿到字节原文，但要改每台客户端的 Fluent Bit 配置并重启，覆盖不到"配置下发不了"的机器，且存量数据仍然没有存证——**作为增强项登记进 `TODO.md`，不作为本次修复**。
  - ③ 整条 JSON 规范化：覆盖全部字段、不依赖采集端变更、服务端可自洽复算——**采用**。
- 后果与已知边界：
  - **两侧存证语义不再等价**。Linux 的 `raw_log` 是采集端字节原文；Windows 的 `raw_log` 是服务端反序列化后重新规范化的文本，键序、空白、数字字面量与重复键在 `json` 解析阶段已定型。所以 Windows 存证证明「服务端收到的这条事件内容未被服务端改动」，**不能**证明「采集端发出的字节流未经中间环节篡改」。这一点必须让使用方知道，已写入 `docs/DATABASE.md` §3.2、`docs/API.md` §5 与页面「算法与策略」区。
  - 复算不依赖重新序列化：`raw_log` 存的就是被哈希的那个字符串，校验端 `SHA2(CONCAT(IFNULL(log_timestamp,''), CHAR(31), raw_log), 256)` 原样适用，**无需改动 SQL**。
  - 规范化参数是哈希口径的一部分：改 `sort_keys`/`separators`/`ensure_ascii` 任一项，会让已写入的全部 Windows 存证被判 `HASH_MISMATCH`。已由 `tests/test_hashing.py` 的规范化 JSON 用例与 SQL 复算对齐用例锁住。
  - `source` 列对 Windows 回退取 `SourceName`（Provider 名），否则存证台账「来源」列对全部 Windows 记录显示为空。
  - **存量无法补齐**：2026-10-15 之前入库的 441,408 行 Windows 日志没有保存原文，无法事后重算。经用户确认「只修往后」，不做历史重放。
  - 「日志总量」与「存证总数」仍不会相等（Linux 侧还有约 229,285 行早于存证功能上线的历史数据），两个指标并排展示本身有误导性，已作为待办登记。

## ADR-019：服务端更新用独立 systemd 单元执行，而不是普通后台进程

- 状态：已采用（2026-10-15）
- 背景：需要在页面上加一个「拉取最新代码并重启服务」的按钮。更新必须停掉当前服务（`systemctl stop log-fusion`），却又不能连带把执行更新的进程一起杀掉。候选：
  - 方案①：由后端进程 `subprocess` 执行更新脚本（同步或后台）。systemd 停止服务时会清理它**整条 cgroup**，脚本会和服务一起被杀，更新半途中断。
  - 方案②：用 `setsid`/`nohup` 把脚本脱到后台。`nohup` 只屏蔽 SIGHUP，**挡不住 cgroup 清理**，同样会被杀。
  - 方案③：用 `systemd-run` 起一个独立的 transient 单元。
- 决策：接口把 `deploy/update-log-fusion.sh` 复制到**仓库之外**的 `/usr/local/bin/log-fusion-update.sh`，再用
  `systemd-run --unit=log-fusion-update --collect --description=... /bin/bash <脚本>` 启动后立即返回；
  脚本自己负责停服 → 拉取最新代码 → 装依赖 → 启动 → `/health` 自检；「如何拉取代码」已由 ADR-020 定为原地 `git reset --hard`。
  已有同名单元在运行则返回 409；服务器没有 `systemd-run` 则返回 500。
- 原因：transient 单元由 systemd 直接托管、**不属于 `log-fusion` 的 cgroup**，停服不影响它；`--collect` 自动回收失败残留。
  脚本复制到仓库外，是因为更新过程会重写仓库内的 `deploy/update-log-fusion.sh`，而 bash 是边读边执行脚本的，
  正在执行的脚本文件被改写会导致执行错乱。
- 后果：
  - 更新日志进 journal：`journalctl -u log-fusion-update -f`；同时写 `/var/log/log-fusion-update.log`。
  - 依赖 systemd 与 `systemd-run`；非 systemd 环境只能 SSH 手工执行脚本（见 `docs/DEPLOY.md` §5）。
  - 接口**无鉴权**（与全站一致），等于把重部署权限交给任何可达者，仅适用于受控内网/测试环境；加鉴权已登记 `docs/TODO.md`。
  - 脚本用 `flock` 防止并发更新；取代码的具体方式（原为删目录重 clone）见 ADR-020。
  - 归档目录 `data` 与 `backend/data` 都写在 `.gitignore` 里，原地更新不会碰它们（见 ADR-020）。
- 备选与否决：方案①（同 cgroup 会被一起杀）、方案②（`nohup` 挡不住 cgroup 清理）均**否决**，理由如上。

## ADR-020：更新脚本改用原地 git 更新，放弃「删目录重新 clone」

- 状态：已采用（2026-10-15），取代 ADR-019 中「先克隆到临时目录、成功后才替换」的取代码方式
- 背景：服务器上的 `/opt/log-fusion` 本来就是 `git clone` 出来的工作树。原脚本为了不丢 `.venv`/`.env`/`data`，
  要在停服后把它们搬到 `/root/lf-keep`、删掉整个目录、重新 clone、再搬回来，逻辑长且每步都可能出错。候选：
  - 方案①：删目录重新 clone（原方案）。需要搬移 + 回滚逻辑；慢（每次全量下载）；磁盘瞬时占用翻倍。
  - 方案②：原地 git 更新——`git fetch` 后 `git reset --hard origin/main`。运行期文件靠 `.gitignore` 保护。
- 决策：采用方案②。更新流程变为 `systemctl stop` → 备份未提交改动为 patch → `git fetch --prune` → `git reset --hard origin/main` → 按需 `pip install` → `systemctl start` → `/health` 自检。
- 原因：`.venv`、`backend/.env`、`data/`、`backend/data/` 都在 `.gitignore` 里，而 **git 从不修改未跟踪/被忽略的文件**，
  所以 `reset --hard` 天然跳过它们，搬移与回滚逻辑整段不再需要；更新是增量的，且保留 `.git` 历史。
  用 `reset --hard origin/main` 而不是 `git pull`：服务器只应镜像远端，`pull` 在本地历史与远端分叉时会产生合并/冲突，`reset` 直接对齐。`.gitignore` 与脚本的行为由 `tests/test_main_contracts.py` 断言锁定。
- 后果：
  - **前提：服务器只拉取、不改代码。** 对已跟踪文件的未提交改动会被 `reset --hard` 覆盖；脚本会先备份成 `/root/lf-keep/pre-update-<时间戳>.patch`，但这不是常规工作流。
  - **严禁 `git clean`**：`git clean -fdx` 会删掉 `.env`、`data`、`.venv`，即 `.gitignore` 正在保护的东西；测试会断言脚本不含 `git clean` / `rm -rf`。
  - 服务器上未跟踪且未忽略的文件（如 `backend/fluent-bit-config/`）不受影响；但若远端新增同名路径，`reset` 会覆盖/删除它，脚本会在动手前打印这些路径。
  - 需要 `/opt/log-fusion` 是健康的 git 工作树；不是（例如当初是手工拷上去的）则中止并提示按 `docs/DEPLOY.md` §2 重新 clone。
- 备选与否决：方案①**否决**——在被 `git` 与 `.gitignore` 已经解决的问题上增加搬移/回滚复杂度，且每次全量拉取、磁盘占用翻倍。


## ADR-021：安全产品日志采用时间拆分、事务断点和显式采集开关（2026-10-16）

三类日志数量约六百万，不采用不受限深分页。固定历史窗口，按计数二分为一次第一页可取全的窗口；分界重叠由稳定身份去重，数据与检查点同事务提交。完整 JSON 保留未知字段，内容冲突不覆盖。后台与 CLI 共用采集实现及 MySQL 会话锁，避免多个进程推进同一断点。

后台开关默认 false，用户显式 CLI 可在停服或只读服务旁补录，完成后退出；按用户最新指示不自动运行大量采集。前端单独展示安全产品数据和进度，不混入 Linux/Windows 统计或现有存证。增量默认回看十分钟，超出窗口的迟到数据由再次历史核对覆盖；设备保留期变化不保证查询快照稳定。

### ADR-021 补充：历史导入达到需求后，后台仅跟踪最新数据

用户明确表示已有导入量足够，不要求完成剩余历史。因此 backend 固定 live_only，不自动创建/续跑历史任务；CLI 默认也仅实时。启动回看 120 秒，运行中故障恢复最多回看 600 秒，允许舍弃更早的未采集间隙；这是用户选择的近期采集范围，不等价于无缝历史补齐。未完成历史标 stopped，保留窗口和旧数据；后台默认开启。完整历史仍仅由显式 --history-only 命令触发。本补充取代原 ADR 关于默认关闭、后台交替补录的描述。

## ADR-022：分类日志的「原始详情」复用列表返回的整行，不新增按 id 查询的接口（2026-10-16）

- 状态：已采用
- 背景：「融合日志管理」新增 5 个分类日志子菜单（Linux 认证会话 / 进程与命令执行 / 文件对象访问、Windows Application / Security），每行最右侧需要「原始详情」。候选：
  - 方案①：仿安全日志页，新增按主键查单条记录的接口。
  - 方案②：列表接口加 `full=true` 返回整行，详情由前端直接展示该行 JSON。
- 决策：采用方案②。`query_category(..., full=True)` 按各平台真实列取整行，响应同时给出 `columns`（表格展示列）。
- 原因：**Linux 的 7 张审计表没有统一主键**（`docs/DATABASE.md` §10 明确「代码查询不依赖统一 id」），按 id 查详情无法实现；改用多字段组合匹配，遇到重复记录会取错行。方案②不依赖任何键，且列表与详情来自同一次查询快照，不会出现「列表旧、详情新」的错位。
- 后果：
  - `full=true` 时单页响应更大（Windows 含 `eventdata`）；页大小固定 30 条，实测可接受。
  - `items` 的字段集合与 `columns` 不再一致：渲染表格必须用 `columns`，不要用 `Object.keys(item)`，否则 Windows 的 `eventdata` 会挤进表格。
  - 详情是**打开列表那一刻的快照**；刷新列表后才能看到该行最新内容（日志表只追加，实际影响可忽略）。
- 备选与否决：方案① 对 Windows 可行、对 Linux 不可行；为两个平台维护两套详情机制不划算，故否决。

## ADR-023：分类日志的事件维度在 Linux 侧用 type，而不是 event_id（2026-10-16）

- 状态：已采用
- 背景：分类日志页需要按「事件 ID」统计并画饼图 / 横向柱状图。实测（2026-10-16，本机库）：
  - `authentication_session` 169,746 行 / **169,690** 个不同 `event_id`，最大一类 3 条；
  - `process_command_execution` 50,067 行 / 8,440 个，最大 9 条；
  - `file_object_access` 51,247 行 / 8,412 个，最大 18 条；
  - `application_logs` 119,852 行 / 145 个，最大 31,958 条；`security_logs` 197,494 行 / 51 个，最大 68,059 条。
- 决策：Windows 两张表按 `event_id` 分组；Linux 三张表按审计记录类型 `type` 分组。响应里的 `groupBy` 明示实际分组列。
- 原因：Linux 的 `event_id` 是审计流水号（几乎每行唯一），按它统计得到的图没有信息量；`type`（SYSLOG / USER_AUTH / EXECVE / PROCTITLE …）才是 Linux 侧稳定的事件类型。
- 后果：
  - Linux 三页的图标题是「事件类型统计」，Windows 两页是「事件 ID 统计」，口径不混淆；
  - 图例说明：`catalog.WINDOWS_EVENT_LABELS` / `LINUX_TYPE_LABELS` 收录常见编号；Application 未收录的编号回退到该编号下最常见的 `provider_name`；都没有时只显示编号，不臆造含义；
  - 两张图最多 10 类，其余在 `rest` 里给出类数与条数（页面注明「另有 N 类未展示」）。
- 备选与否决：严格按 `event_id` 统计三张 Linux 表——实测前 10 类各只有 3～18 条，属于无意义图表，否决。


## ADR-024：WAF/DAS Syslog 采用独立接收进程与先落盘缓冲（2026-10-28）

- 状态：独立进程决策已被 ADR-025 取代；六表和先落盘缓冲仍沿用，真实库未迁移。
- 决策：在 backend/app 内实现独立 TCP/UDP CLI，先 SQLite WAL/FULL 提交，再按产品原生字段解析并写 LOG_FUSION_DB 六张专用表；每表都保留完整 raw_log、raw_bytes 和 payload。WAF 按三大组、DAS 按 audit/session/warn 分表；log_type 存细分类，不套用现有截图字段。SQL 需显式执行，不挂到现有 Base.create_all。
- 原因：HTTP 8080 不能直接接收 Syslog；Web 重载不应同时中断接收。内存队列无法跨重启重放。不同产品字段、严重度和动作语义不等价，不强造 acted 或把执行结果伪装成实际动作。
- 重放：业务提交后才确认本地队列，稳定 ingest_id 处理远端已提交/本地未确认的窗口；不同接收事件即使内容相同也保留。不据文档推断 ssid/correlation_id 等为唯一键。
- 后果：新增独立进程和 SQLite 文件的运行维护，磁盘容量/备份/服务注册待配置；TCP 没有业务级确认，UDP 仍可能丢包，不承诺端到端零丢失。未知/损坏报文隔离，修正规则后显式重放。未新增前端与 HTTP 查询，未联动现有存证库；详细约束见 SYSLOG.md。


## ADR-025：Syslog 默认随 run.py 的应用生命周期启停（2026-10-28）

- 状态：已采用；用户明确要求运行 run.py 时同时接收 WAF/DAS，无需另外开进程。
- 决策：app.main.lifespan 等待两个启用的监听器完成绑定，再对外就绪；WAF 5514、DAS 5515 默认 TCP/UDP。配置由环境或 backend/.env 注入，支持全局与按产品关闭、改端口、来源列表等。导入模块不绑定端口；仍保持单 worker，避免 reload 父子或多 worker 重复监听。
- 退出与失败：关闭监听并等待本地提交，取消并收尾在途写库，再关闭 SQLite/连接池；第二个接收器绑定失败也清理第一个，不允许静默降级为“HTTP 正常、接收未启用”。MySQL 故障不影响原文落盘。独立 CLI 保留作高级调试/状态/重放，启用前先关闭应用中对应接收器。
- 代价：Web 重载、服务更新会同时短暂停止接收；SQLite 保留已提交报文并在下次启动续写，但不能覆盖尚未收到的数据，UDP 仍有丢失窗口。部署沿用现有 systemd 主服务，不另注册两个接收服务。六表 DDL、原文和哈希规则、HTTP/WebSocket 行为不变。
