存证口径说明
每条采集日志入库时按 sha256(timestamp + 0x1F + log) 计算摘要，原文与摘要一起写入 log_hash.log_hash；本页逐条复算并分类为「校验一致 / 哈希不一致 / 原文缺失」。摘要只能证明原文与摘要自洽，若要防止持库权限者伪造自洽记录，需启用 HMAC 签名（见「算法与策略」）。

存证归档
按入库时间导出 CSV 并从数据库中删除；导出文件确认落盘后才会执行删除，失败时不删除任何记录。
自动归档阈值： 个日历月之前的存证（按入库时间），由后台任务每天执行一次。


算法与摘要定义
摘要算法 SHA-256，摘要版本 EVIDENCE-V1；输入为 raw_text(log_timestamp) + "\x1F" + raw_text(raw_log)，不做 trim 或归一化，缺失时间戳按空串计算。存证原文按平台不同：Linux 取采集载荷的 log 字段原文；Windows 的 winlog 载荷没有 log，改取整条记录规范化后的 JSON（键排序 + 紧凑分隔符 + 非 ASCII 不转义）。写入端与校验端使用同一规则，任一端改动都会让全部存证被判成篡改。
当前边界
SHA-256 只能证明「原文与摘要自洽」。具备写库权限的人可以同时改写原文和摘要，构造出自洽的假记录——这类伪造检测不出来，需要 HMAC-SHA256（密钥仅服务端持有）或外部不可篡改存储做交叉校验。两侧覆盖范围不等价：Windows 的 raw_log 是服务端反序列化后规范化的 JSON，不是采集端字节原文，因此只证明「服务端收到的这条事件内容」，不证明采集端到服务端之间未被改动。
保留与归档
默认保留  个日历月的存证，超期由后台任务导出 CSV 后删除；归档文件与台账是事后追溯的唯一依据。



系统维护
服务端代码更新与重启
更新服务端代码
从 GitHub 拉取最新代码：停止当前服务 → 替换 /opt/log-fusion → 重装依赖 → 重新启动。更新为整目录替换，.venv、backend/.env、data 会原样保留，不会丢失配置与归档文件。
更新期间服务会短暂中断（约 10–30 秒），页面会自动等待并刷新。请勿在采集高峰期操作。
更新在服务器上以独立 systemd 单元 log-fusion-update 执行；查看日志：journalctl -u log-fusion-update -f
